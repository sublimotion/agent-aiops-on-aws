# Qwen3-235B-A22B Serving Benchmark (Blackwell B300)

## Status: DRAFT (2026-04-22)

## Overview

Deploy Alibaba's **Qwen3-235B-A22B** (`Qwen/Qwen3-235B-A22B-FP8`) on p6-b300.48xlarge (8x B300 NVSwitch Blackwell) to benchmark serving performance with a dual-engine comparison between vLLM and SGLang.

Qwen3-235B-A22B is a 235B MoE model (128 experts, top-8 routing, 22B active per token) with GQA attention, 94 layers, togglable thinking mode, and 131K context via YaRN. At only ~235GB in FP8, it leaves **massive** KV cache headroom on B300's 2.15TB VRAM — making this the ideal platform for extreme concurrency testing.

**Why this model:**
- Apache 2.0 license, strong open-source community
- 22B active params — efficient MoE with low per-token compute cost
- Thinking mode toggle — reasoning-heavy or fast inference per request
- Tool calling support (`qwen3` parser in both vLLM and SGLang)
- FP8 variant available (fine-grained FP8, block size 128)
- 53 quantized community variants (GGUF, AWQ, GPTQ) — ecosystem depth

**Why B300 spot:**
- ~$15/hr spot vs ~$98/hr p5e capacity block — 6.5x cheaper per GPU-hour
- 2.15TB VRAM for a ~235GB FP8 model = ~1.85TB KV cache headroom
- NVLink 5 / NVSwitch — full bisection bandwidth for TP8
- sm_103 with CUDA 13.0 — data center Blackwell, mature kernel support

**Key hypothesis:** With only ~29GB model weights per GPU (FP8 TP8), each B300 GPU retains ~231GB for KV cache — far more than any previous benchmark. This should enable **extreme concurrency** (256-1024+ concurrent sessions at 32K context), potentially making Qwen3-235B the most cost-efficient self-hosted coding agent backbone.

**Comparison targets:**

| Model | Active Params | VRAM Usage (FP8 TP8) | KV Headroom (B300) | Instance |
|---|---|---|---|---|
| **Qwen3-235B-A22B** (this spec) | 22B | ~235 GB | ~1,850 GB | p6-b300 spot |
| Kimi K2.6 (1T MoE) | 32B | ~594 GB (INT4) | ~1,490 GB | p6-b300 spot |
| GLM-5 (744B MoE) | 40B | ~756 GB (FP8) | ~780 GB | p6-b200 |
| Qwen3.5-MoE-A3B (3B active) | 3B | ~7 GB | ~2,080 GB | g7e |

#### Serving Configuration — Track A: vLLM

```bash
vllm serve Qwen/Qwen3-235B-A22B-FP8 \
  --tensor-parallel-size 8 \
  --reasoning-parser deepseek_r1 \
  --tool-call-parser qwen3_xml \
  --enable-auto-tool-choice \
  --enable-prefix-caching \
  --max-model-len 131072 \
  --gpu-memory-utilization 0.92 \
  --max-num-seqs 512 \
  --host 0.0.0.0 --port 8000
```

Notes:
- `--reasoning-parser deepseek_r1` per official Qwen3 docs for vLLM
- `--tool-call-parser qwen3_xml` for Qwen3 tool calling (uses XML format internally)
- `--gpu-memory-utilization 0.92` — safe with only ~29GB weights per GPU
- `--max-num-seqs 512` — push concurrency limit given massive KV headroom
- `--max-model-len 131072` — YaRN-extended context
- `--disable-log-requests` removed — flag no longer exists in vLLM v0.19.1 (K2.6 lesson)
- `--enable-reasoning` removed — not a valid vLLM flag; reasoning parser alone is sufficient

**AOT compilation cache** (persist across restarts):

```bash
export VLLM_TORCH_COMPILE_CACHE=/mnt/nvme/vllm-cache
export TRITON_CACHE_DIR=/mnt/nvme/triton-cache
```

#### Serving Configuration — Track B: SGLang

```bash
python -m sglang.launch_server \
  --model-path Qwen/Qwen3-235B-A22B-FP8 \
  --tp 8 --trust-remote-code \
  --reasoning-parser qwen3 \
  --host 0.0.0.0 --port 8000 \
  --mem-fraction-static 0.88 \
  --context-length 131072
```

**With HiCache (Track B2):**

```bash
python -m sglang.launch_server \
  --model-path Qwen/Qwen3-235B-A22B-FP8 \
  --tp 8 --trust-remote-code \
  --reasoning-parser qwen3 \
  --host 0.0.0.0 --port 8000 \
  --mem-fraction-static 0.88 \
  --context-length 131072 \
  --enable-hierarchical-cache \
  --hicache-size 250
```

`--hicache-size 250` = 250 GB host memory **per TP rank** (2 TB total across 8 ranks). K2.6 lesson: 500 GB/rank hangs indefinitely (4 TB exceeds available RAM after model + OS). 200 GB/rank proven safe; 250 GB/rank should work for this lighter model (~29 GB weights/GPU vs ~72 GB for K2.6). With only ~29GB weights per GPU, the GPU KV pool is ~231GB — HiCache extends this with host memory spill at extreme concurrency.

**Fast warmup:**
```bash
export SGLANG_JIT_DEEPGEMM_FAST_WARMUP=1  # <3 min cold start
```

### P0: Smoke Test + Gate

| Step | Test | Pass Criteria |
|---|---|---|
| 0a | Health check | `/v1/chat/completions` responds on both engines |
| 0b | Basic inference | 1K input / 512 output, verify correct output |
| 0c | Thinking mode | `enable_thinking=True`, verify `<think>` tokens present |
| 0d | Non-thinking mode | `enable_thinking=False`, verify no thinking tokens |
| 0e | BFCL tool-call | 50 scenarios (coding agent tool suite) |
| 0f | Tool + thinking | Tool call with thinking enabled — verify both work together |

**Tool definitions** (coding agent relevant):

```json
[
  {"name": "read_file", "parameters": {"path": "string"}},
  {"name": "write_file", "parameters": {"path": "string", "content": "string"}},
  {"name": "run_command", "parameters": {"command": "string", "timeout": "integer"}},
  {"name": "web_search", "parameters": {"query": "string"}},
  {"name": "list_directory", "parameters": {"path": "string", "recursive": "boolean"}},
  {"name": "grep_codebase", "parameters": {"pattern": "string", "file_glob": "string"}}
]
```

**Gate**: BFCL >= 75% on at least one engine → proceed to P1. If < 75% on both → STOP.

### P1: Standard W1-W6 Suite (All Configs)

| Workload | Pattern | Input/Output | Focus |
|---|---|---|---|
| **W1** | Multi-turn chat | 1024/128 tok, rounds 1/5/10 | TTFT + ITL baseline, prefix sharing |

### P2: Extreme Concurrency Sweep + HiCache Deep-Dive

**The headline experiment.** With ~1,850GB KV headroom, this is the largest concurrency sweep we've attempted.

**Concurrency sweep** (all 3 configs, at optimal QPS from P1):

| Concurrency | Purpose | Expected KV Usage (32K ctx) |
|---|---|---|
| 1 | Single-stream baseline | < 1% |
| 8 | Light batch | ~2% |
| 32 | Moderate | ~8% |
| 64 | Comfortable | ~16% |
| 128 | Heavy (GLM-5 HiCache peak) | ~32% |
| 256 | Stress | ~64% |
| 512 | Extreme — unique to this model | ~100% (GPU VRAM limit) |
| 768 | HiCache-only territory | GPU full → HiCache spill |
| 1024 | Ceiling test | Deep into HiCache |

At 32K context per request, estimated KV per session is ~3.5GB (GQA with 4 KV heads across 94 layers). This means:
- GPU-only: ~1,850GB / 3.5GB ≈ **528 concurrent sessions** theoretical max
- With 250GB/rank HiCache (2TB total): ~3,850GB / 3.5GB ≈ **1,100 concurrent sessions** theoretical max

The sweep should find where SLO violations begin (TTFT > 2s, ITL > 100ms).

**HiCache comparison** at each concurrency level:

Compare `sglang-tp8-radix` vs `sglang-tp8-hicache`. The crossover point where HiCache matters should be at ~400-500 concurrency (when GPU VRAM KV fills). Below that, HiCache adds no benefit.

**Thinking mode under load:**

Run the concurrency sweep with thinking enabled at selected levels (64, 256, 512) to measure the overhead of thinking tokens on throughput and latency at scale.

### P3: Coding Agent Simulation + Economics

**Goal**: Determine maximum concurrent coding agents and cost-per-engineer.

#### Agent Profile

| Parameter | Value |
|---|---|
| Requests per engineer per hour | 30-60 |
| Avg input tokens per request | 4,000 |
| Avg output tokens per request | 1,500 |
| Tool calls per request | 1.5 |
| Active coding hours per day | 6 |
| Peak concurrency factor | 0.4 |

#### Agent Simulation (12 scenarios)

Each simulated agent follows a multi-turn coding workflow:

```
Agent workflow (per session):
1. Receive task prompt (bug fix / feature / refactor)
2. Read file(s) via tool call           → 2K-8K tokens context
3. Analyze + plan (model thinking)      → 500-2K tokens output
4. Write fix via tool call              → 1K-4K tokens output
5. Run tests via tool call              → wait 5-30s (simulated)
6. Analyze results                      → 500-1K tokens
7. Iterate (steps 4-6) x 2-3 cycles
```

Run at SLO-max concurrency from P2 to validate functional correctness under load.

#### Economics

**Self-hosted Qwen3-235B on B300 spot:**

```
Monthly cost = spot_rate x hours/month
             = ~$15/hr x 730 hrs/month (24/7)
             = ~$10,950/month

Engineers supported = SLO-max concurrent agents / peak concurrency factor
Cost per engineer per month = monthly cost / engineers supported
```

**Break-even analysis:**

| Scenario (SLO-max agents) | Cost/eng/month | vs Sonnet ($205) | vs Opus ($1,025) |
|---|---|---|---|
| 64 | ~$684 | 3.3x worse | 1.5x better |
| 128 | ~$342 | 1.7x worse | 3.0x better |
| 256 | ~$171 | **1.2x better** | 6.0x better |
| 512 | ~$86 | **2.4x better** | 11.9x better |

**Key insight**: At $15/hr spot pricing, Qwen3-235B needs only ~128 agents to beat Opus and ~256 to beat Sonnet. The massive KV headroom makes 256+ plausible — this could be the first model where self-hosted beats Claude API on pure economics.

## Non-Requirements

- BF16 deployment (~470GB — FP8 is smaller and leaves more KV headroom)
- Multi-node distributed inference (single p6-b300.48xlarge)
- GPTQ/AWQ quantization (FP8 preferred for accuracy; GPTQ had issues with Qwen3.5 MoE)
- Vision/multimodal (Qwen3-235B is text-only)
- LMCache integration (blocked for GQA models at this scale)
- Production autoscaling
- Multi-region deployment

- EKS RBAC with least-privilege service accounts
- Private subnets, no public endpoints on GPU pods
- Model weights on local NVMe (ephemeral with instance)

## Known Limitations

1. **FP8 distributed inference bug**: `transformers` FP8 has distributed inference issues — must set `CUDA_LAUNCH_BLOCKING=1` for multi-device. vLLM/SGLang may not be affected (they use their own FP8 kernels)
2. **Spot reclaim risk**: Spot instances can be terminated with 2 min warning. Checkpoint results between P-tiers. Model re-download (~235GB) takes ~8 min from S3 to NVMe
3. **B300 AMI requirement**: Must use AL2023 NVIDIA AMI (not AL2). AL2 kernel lacks `ib_umad` module required for Fabric Manager on NVL5+
4. **DeepGEMM JIT cold start**: ~15 min on first startup. Use `SGLANG_JIT_DEEPGEMM_FAST_WARMUP=1` for SGLang (<3 min) and AOT cache for vLLM
5. **YaRN context extension**: 131K context via YaRN may have quality degradation beyond 32K native. Test quality at 64K and 128K during P1 W6
6. **vLLM reasoning parser**: Official docs use `deepseek_r1` parser for vLLM (not `qwen3`). Verify thinking tokens parse correctly
7. **Qwen3 MoE GPTQ issues**: Qwen3.5 MoE GPTQ-Int4 produced garbage on vLLM 0.18 (`gptq_marlin` incompatible). FP8 avoids this entirely
8. **Concurrency estimates are theoretical**: KV per session depends on actual sequence lengths, not just `max_model_len`. Real concurrency ceiling will be lower than the 528 theoretical max
9. **Tool calling parser**: vLLM uses `qwen3_xml`, SGLang uses native `qwen3` — behavior may differ. Test both in P0
10. **HiCache 500GB/rank OOMs on B300** (K2.6 lesson): `--hicache-size` is per-rank, not total. 500 GB x 8 = 4 TB exceeds available RAM. Max safe: ~250 GB/rank. Pod hangs indefinitely with no error — hard to diagnose
11. **EKS managed node groups unreliable for spot B300** (K2.6 lesson): Gets stuck in CREATING. Use self-managed nodes with `aws ec2 run-instances` + nodeadm UserData
12. **vLLM `--disable-log-requests` removed** (K2.6 lesson): No longer valid in v0.19.1. Omit from pod specs
13. **SGLang `reasoning_content` field** (K2.6 lesson): SGLang streaming uses `delta.reasoning_content` (not `delta.reasoning`). Fixed in `benchmark-serving.py` — verify the fix is deployed
14. **vLLM FLASHINFER_MLA dominates SGLang on B300** (K2.6 lesson): vLLM achieved 3.1x higher throughput at c=512 (10,437 vs 3,400 tok/s). Expect vLLM to win on this model too, especially under load. SGLang advantage is cold start speed only

## Open Questions

1. **SGLang tool-call parser for Qwen3**: Does SGLang v0.5.10 support Qwen3 tool calling natively, or does it need `--tool-call-parser` flag? The model card only mentions `--reasoning-parser qwen3`
2. **FP8 fine-grained on B300**: Qwen3-235B-A22B-FP8 uses block-size-128 fine-grained FP8. Verify B300 sm_103 kernels handle this format (should — it's standard E4M3)
3. **Thinking mode + tool calling interaction**: When both thinking and tool calling are enabled, verify the model doesn't produce malformed output (thinking tokens inside tool call blocks)
4. **GQA KV cache size**: With only 4 KV heads (vs 64 Q heads), the actual KV cache per token is very small. Real concurrency ceiling may be higher than the 528 estimate
5. **Quality at scale**: Does Qwen3-235B produce comparable quality to frontier models for coding tasks? BFCL gate (P0) and agent simulation (P3) will answer this
