## Analysis

### Key findings from this compound run

**SGLang + Blackwell bring-up is a minefield of compatibility issues.** Five separate framework-level constraints had to be discovered and worked around to get Qwen3-Next running on g7e: cutlass backend, triton attention, CUDA graph disabled, cu130 image tag, and MoE/FP8 kernel tuning gaps. None of these are documented in SGLang's quickstart guides. These are now encoded as steering rules to prevent the next Blackwell deployment from burning GPU hours on discovery.

**Tool-call parser bugs in both SGLang and vLLM create silent multi-turn failures.** SGLang's qwen3_coder parser outputs XML instead of the OpenAI-spec tool_calls array; vLLM's Mistral parser generates `call_0` instead of 9-character alphanumeric IDs. Both bugs cause BFCL multi-turn scores to drop from ~100% to 66-75% on models that are otherwise excellent at tool use. Downstream agent frameworks must now handle both formats until upstream fixes land.

**HiCache hybrid model support was blocked by a PR merge timing issue.** The S3 benchmark (HiCache L2 offloading) could not run because PR #19663 was not yet merged into the nightly build. This is a cautionary tale about assuming nightly builds contain advertised features. The new steering rule requires verifying PR merge status before reserving capacity for feature-gated benchmarks.

**g7e instance characteristics (PCIe, no EFA/GDS) fundamentally constrain serving architecture.** Unlike p5en with NVLink+EFA+GDS, g7e instances require standard file I/O for KV offloading and cannot benefit from GDS-accelerated FSx. The multi-replica vs shared-KV-cache trade-off is now documented: isolated replicas (vLLM TP=1 per GPU) have zero failures but 4-5x higher TTFT; shared KV cache (SGLang TP=4) has lower latency but saturates under load. This architectural decision is now a steering rule for future PCIe-based deployments.

**Force-deleted pods leak GPU memory, requiring manual PID cleanup.** This is a Kubernetes + NVIDIA driver interaction bug that has wasted hours across multiple blueprints. It's now a steering rule with explicit `nvidia-smi` + `xargs kill -9` remediation steps.

### Recommendations for next deployment

1. **Add readiness audit before capacity blocks.** This blueprint bypassed the standard audit cycle by running on a bare EC2 instance. The lack of pre-flight checks meant 8 compatibility issues were discovered during the billable GPU session. A readiness audit would have caught at least 4 of them (image tag, DeepGemm backend, HiCache PR status, MoE kernel tuning).

2. **Test SGLang nightly builds on CPU instances before GPU sessions.** The cutlass backend, triton attention, and CUDA graph constraints could all have been discovered on a g6e.xlarge or even a c7g instance by attempting model load with the target flags. Reserve the GPU hours for actual benchmarking, not framework compatibility discovery.

3. **Document benchmark methodology in a separate artifact.** The lessons.md file mixes bring-up findings, benchmark results, and head-to-head analysis. Consider splitting into `lessons.md` (deployment), `benchmark-report.md` (results + analysis), and `methodology.md` (how to reproduce). This would make it easier for future compound runs to separate cross-cutting lessons from benchmark-specific data.

4. **Consider upstreaming tool-call parser fixes.** Both the vLLM Mistral ID format bug (#23180) and SGLang's XML output format are blockers for production agent deployments. These bugs affect all users of those models, not just this blueprint. Filing issues with reproduction steps + proposed fixes would benefit the community and reduce the need for downstream workarounds.
