## Recommendations

### Deployment
1. **Use vLLM as default for Kimi K2.6 on B300** — 2-3x lower TTFT, 3.1x higher throughput at scale. Only use SGLang when cold start time is critical (spot instances with frequent interruptions).
2. **Always use -cu130 container tags for B200/B300** — sm_100f/sm_103 require CUDA 13.0. Standard tags fail.
3. **HiCache is not a silver bullet** — Provides dramatic single-stream improvements but no benefit at high concurrency. The bottleneck shifts to compute. Use HiCache for low-concurrency workloads only.
4. **EKS managed node groups are unreliable for spot B300** — Launch instances directly via EC2 run-instances with self-managed EKS joining.

### Benchmarking
1. **Run pressure tests to find concurrency ceiling** — B300's 2.15TB VRAM allows dramatically higher concurrency than smaller GPUs. vLLM scaled linearly to c=512; SGLang saturated at c=128.
2. **Test both engines when optimizing** — vLLM and SGLang have complementary strengths. vLLM dominates latency/throughput, SGLang dominates cold start time.
3. **Update benchmark-serving.py for reasoning_content** — SGLang and vLLM v0.19+ use `reasoning_content`, not `reasoning`. Add fallback to avoid 0ms TTFT/0.0 TPS false results.

### Cost Optimization
- **B300 spot is ~500x cheaper than K2.5 p5e capacity block** — $0.43/1M tokens (c=512, vLLM) vs ~$217/1M tokens (K2.5 p5e, single-stream extrapolated). B300 spot at ~$16/hr vs p5e capacity block at ~$98/hr.
- **16-35x cheaper than Claude API** — K2.6 self-hosted on B300 spot vs Claude 3.5 Sonnet API ($15/1M).
