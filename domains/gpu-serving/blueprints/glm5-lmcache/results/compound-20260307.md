## Analysis

### Cross-cutting infrastructure lessons (4 elevated)

**Lesson #1 (AL2023 AMI for B200 NVL5+)** is a hard AWS/NVIDIA platform constraint. The ib_umad kernel module requirement for NVIDIA Fabric Manager is not a model quirk or a version-specific bug — it applies to all B200 NVSwitch deployments (p6-b200.* instances). This is a foundational infrastructure rule that prevents catastrophic failures (CUDA error 802, no GPU access from containers despite nvidia-smi showing GPUs).

**Lesson #2 (AL2023 nodeadm MIME format)** is a required workflow change for all EKS deployments on AL2023 AMIs. The user data format shift from `/etc/eks/bootstrap.sh` to `nodeadm` with YAML config in MIME multipart format is not specific to this blueprint — it applies to all AL2023-based EKS node groups.

**Lesson #5 (DeepGEMM JIT warmup)** applies to all Blackwell FP8 serving deployments, not just GLM-5. The 15-minute JIT compilation is a DeepGEMM constraint on Blackwell sm_120 GPUs, affecting any model using FP8 quantization. This is a deployment workflow sequence rule: always budget for JIT warmup time on first startup, and set Kubernetes readiness probe `initialDelaySeconds` accordingly.

**Lesson #10 (LMCache NSA/MLA incompatibility)** is a systemic gap affecting multiple models (GLM-5, DeepSeek V3, and any MLA/NSA model on SGLang). The incompatibility between LMCache's SGLang adapter and `NSATokenToKVPool`'s fused `kv_buffer` is a framework-level constraint, not a model-specific quirk. This blocks a major feature (KV cache offloading) for an entire model architecture family, making it a high-priority steering rule to prevent wasted capacity block time.

### Cross-cutting operational lessons (2 elevated)

**Lesson #6 (B200 termination delay)** applies to all large instance types, especially in capacity block scenarios where slot availability matters. The 10-minute termination delay for p6-b200.48xlarge is an AWS service constraint, not a GLM-5-specific issue. This affects deployment automation (poll intervals, retry logic) and cost planning.

**Lesson #11 (PYTHONPATH NVMe trick)** is a general EKS pattern for AL2023 nodes that lack `buildctl`/`buildkitd`. The workaround (pip install in running container → copy to NVMe hostPath → set PYTHONPATH env) applies to any blueprint that needs to add Python packages without rebuilding images on the node. This is a deployment workflow pattern that reduces friction for rapid iteration during capacity blocks.

### Local lessons (6 kept)

Lessons #3, #4, #7, #8, #9, and #12 are kept local because they are:
- Model-specific (glm_moe_dsa image requirement, memory profile, throughput scaling)
- Configuration detail (SGLang --host flag)
- Platform-specific bug (macOS hf_xet deadlock)
- Dependency version conflict (LMCache dev branch overriding transformers)

These lessons are valuable for GLM-5 operators but do not generalize to other blueprints.

## Recommendations

1. **Add pre-flight check for AL2023 AMI on p6-b200 instances** — the readiness audit should verify AMI name contains "al2023" before proceeding with B200 NVL5+ deployments. This prevents the ib_umad failure mode.

2. **Document LMCache MLA compatibility status in steering** — this is a moving target (PR #2629 is open). The steering rule should include a "check PR merge status before reserving capacity" note to avoid wasted GPU hours.

3. **Consider pre-compiling DeepGEMM kernels** — the 15-minute JIT overhead could be eliminated by running `sglang.compile_deep_gemm` offline and packaging the kernel cache in the container image. This is a potential optimization for future Blackwell deployments.

4. **PYTHONPATH pattern may apply to LMCache itself** — if LMCache remains unmerged in SGLang nightly, the PYTHONPATH NVMe trick could be used to install LMCache from source on the node. This is a workaround for the "Lesson #10 blocked" state.
