Why HiCache shows -2% on long generation

Long generation (500 tokens) at moderate concurrency (16) doesn't trigger KV cache eviction, so HiCache's write-through overhead (CPU memory copies) slightly increases latency. The -2% is within noise margin. HiCache's value appears only under KV cache pressure (high concurrency with short generation).

Key Insights

KV cache was the bottleneck, not compute

Baseline throughput plateaued at 64 concurrent (909 tok/s) while HiCache continued scaling to 128 concurrent (2,602 tok/s). GLM-5 uses 175/183 GB per GPU for weights, leaving only ~9 GB for KV cache. HiCache's 800 GB CPU tier (100 GB/rank) fundamentally changes the concurrency ceiling.

HiCache works where LMCache fails

LMCache expects separate k_buffer/v_buffer but NSA/MLA uses a fused kv_buffer. SGLang's HiCache has native NSATokenToKVPoolHost class that handles the fused layout. For MLA models (GLM-5, DeepSeek V3), HiCache is the only KV offloading option today.

P90 latency improves under load

At 64 concurrent: baseline P90 = 16.55s, HiCache P90 = 8.26s (-50%). With more KV cache capacity, HiCache reduces queuing and recomputation delays, not just throughput.

LMCache Blocked on NSA/MLA

LMCache v0.3.15 crashes on GLM-5: AttributeError: 'NSATokenToKVPool' object has no attribute 'k_buffer'. Fix pending in LMCache PR #2629. Three configs (CPU, GDS, POSIX) remain untestable. HiCache CPU offload serves as the working alternative with 2.86x throughput improvement.
