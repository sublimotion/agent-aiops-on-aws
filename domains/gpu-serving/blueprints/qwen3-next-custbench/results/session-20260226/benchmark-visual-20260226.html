Prefix Caching: The Single Most Impactful Change

With a shared 8K system prompt (realistic for production), prefix caching avoids recomputing the cached prefix for each request. At 1000 concurrent requests, this translates to 82% less TTFT and 77% more throughput. The customer's current config has --no-enable-prefix-caching — removing this flag is the highest-ROI change.

When 490 requests share an 8K-token prefix, the prefix KV blocks are stored once and referenced by all requests. Each request only allocates KV slots for its unique 128-token suffix + output tokens. This is why prefix caching is even more impactful under memory constraints (T5c: 94% TTFT reduction).

T5d: KV Cache Offloading — BLOCKED (4 approaches attempted)

All KV Offloading Approaches Fail with Qwen3-Next

1. --cpu-offload-gb: NotImplementedError: Cannot copy out of meta tensor (FP8 + V1 engine)

2. Dynamo KVBM: dynamo-run: not found (ai-dynamo 0.9.0 removed CLI, ai-dynamo-vllm only goes to 0.8.4)

3. OffloadingConnector: Hybrid KV cache manager disabled, can't unify specs (auto-disables HMA, but Qwen3-Next requires it)

4. LMCacheMPConnector: Same HMA error (no KV connectors support SupportsHMA yet)

Root cause: Qwen3-Next has hybrid attention (different KV cache specs per layer group). All vLLM 0.16 KV connectors auto-disable HMA, which this model requires. Prefix caching (T5c: 94% TTFT reduction) remains the best optimization for memory-constrained scenarios.

Recommendations for Customer

Actionable changes ranked by impact

1. Enable Prefix Caching

Remove --no-enable-prefix-caching (or add --enable-prefix-caching). If the workload has shared system prompts, this delivers 82% TTFT reduction and 77% throughput gain.

2. Enable Chunked Prefill

Remove --no-enable-chunked-prefill. Improves scheduling fairness at high concurrency, prevents head-of-line blocking where one long prefill starves decode iterations.

3. Rate Limit Requests

Cap at 200–500 concurrent requests (or use a queue with rate limiting at 5 qps). This keeps TTFT under 1 second while maintaining high throughput.

4. Consider TP=8

Using all 8 GPUs for one model instance doubles KV cache capacity and prefill throughput. Better for extreme concurrency workloads.

5. Drop MTP for Now

MTP speculative decoding adds complexity and is not available in stable vLLM for this model. At high concurrency, the bottleneck is prefill, not decode.

6. Deploy 2× TP=4 Replicas

Use all 8 GPUs as 2 TP=4 replicas for 84,628 tok/s combined throughput (1.71x scaling). Zero failures at 1500 concurrent. This is the recommended production topology for p5en.48xlarge.
