TL;DR. A single 8×B300 node serves GLM-5.2-FP8 at 9,271 decode tok/s within an 8.1s TTFT p95 (customer SLO 15s) on realistic coding-agent traffic. Two levers carried the whole result: prefix caching (+347%, the 12K shared system prompt was the prefill bottleneck) and the B300-only TP4+DP2 layout (+28%, physically can't run on a 180GB B200). Four levers were tested and rejected: fp8-KV is the model's auto-default (no separate gain), MTP spec-decode regresses −12% at the knee, MNBT/chunked-prefill is a default-is-best wash, and — answering the B200 report's open question — official NVFP4 halves throughput (−52%) on its current experimental MoE kernel. 4 B300 nodes cover the customer's 32,500 tok/s target with margin at $0.45/Mtok (output), on FP8.

Regime story. T0 is prefill-bound — TTFT scales hard with concurrency because every request re-prefills the 12K shared prompt. Prefix cache (T2) removes that, flipping the regime to decode-bound (TTFT then scales linearly; throughput keeps climbing). In the decode-bound regime, fp8-KV is already on by default and MTP's draft overhead is a net loss at batch. The remaining win is structural parallelism: two TP4 replicas beat one TP8 instance (cheaper per-step collectives + 2× scheduler parallelism), each holding the full prefix in its own radix cache. Regime calls are [gauge-inferred] from engine counters — DCGM profiling is non-functional on B300/driver-580 (confirmed via dcgmi); HBM-BW vs compute distinction not directly measured.

5. Method & caveats

  • TTFT is the customer's primary SLO and is measured directly: streaming first-token timing client-side, cross-checked against the SGLang time_to_first_token_seconds histogram in Prometheus (verified live before any paid run — the metric-name underscore gotcha that lost TTFT data on prior engagements was fixed here).
  • Goodput, not raw throughput: every number counts only requests meeting TTFT p95<15s with <0.1% errors. Configs that beat peak tok/s by breaching the SLO do not count.
  • Single-variable discipline: each tier differs from its parent by exactly one lever (diff-verified), so deltas are attributable. Full lineage in the trajectory JSON.
  • Concurrency >c256 certified with a 2-client distributed driver after a single-client socket-exhaustion artifact was root-caused (server was healthy throughout: num_retracted_reqs=0).
  • Quality gate (reward-hacking guard): the winning T4 config passed 3 frozen coding tasks it wasn't tuned on + glm47 tool-calling — goodput is not bought with degraded output.
  • NVFP4 answered: official nvidia/GLM-5.2-NVFP4 (shared-expert-preserved recipe) tested head-to-head on B300 — −52% throughput vs FP8 (same trtllm MoE backend, experimental kernel with deferred-finalize disabled). Confirms the B200 community-checkpoint result transfers to the official recipe. Use FP8 for serving; NVFP4 only for VRAM-constrained fit or (untested) c1 latency.
  • Not yet tested: the spec's large-ISL (64K) coding-agent workload (this run characterized the 12K-prefix profile); HiCache. Deferred within budget.
