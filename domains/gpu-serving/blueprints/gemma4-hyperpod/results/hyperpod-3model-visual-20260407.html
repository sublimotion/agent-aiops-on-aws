Why is the 4B model faster at 16K than the 31B?
Both Gemma models use TRITON_ATTN (forced by heterogeneous head_dim 256/512). But the 31B has 8x more parameters to prefill. Mistral SM4, despite being 119B total, uses MLA + FlashAttention with only 6.5B active params per token, giving it better long-context TTFT than the 31B dense model.

Key Findings

1. TRITON_ATTN is the dominant performance factor
Both Gemma 4 variants force TRITON_ATTN due to heterogeneous head_dim (256 local + 512 global). This backend is significantly slower for prefill on H100 than FlashAttention. Mistral SM4, despite being 4x larger (119B vs 31B), has better long-context TTFT because it uses FLASH_ATTN_MLA with only 6.5B active params. Takeaway: Attention backend matters more than model size for prefill latency.
2. Prefix caching equalizes all three models
With prefix caching at 16K, all three models deliver sub-200ms TTFT: Gemma E4B (98ms), Mistral SM4 (103ms), Gemma 31B (161ms). The model with the worst uncached TTFT (Gemma 31B) gets the biggest cache benefit (11.1x). For RAG/agentic workloads with shared system prompts, prefix caching is the great equalizer.
3. Small models dominate throughput on H100
Gemma 4 E4B on a single H100 delivers 5,158 output tok/s at QPS=20 — more than 2x the 31B (1,188) and 2.4x Mistral SM4 (2,160). For high-throughput, low-latency use cases, the 4B model is the clear winner. TTFT stays under 160ms even at QPS=20.
4. MoE delivers best ITL-per-parameter
Mistral SM4's MoE architecture (6.5B active of 119B total) achieves 5.9ms ITL p50 — the best of all three models. Dense models pay a proportional ITL cost: 7ms for 4B, 17ms for 31B. MoE only pays for active parameters during decode.
5. Three models colocated on one p5.48xlarge
All three models ran simultaneously on a single ml.p5.48xlarge using 5 of 8 GPUs: Mistral SM4 (2 GPUs, TP2), Gemma 31B (2 GPUs, TP2), Gemma E4B (1 GPU, TP1). This demonstrates efficient multi-model serving on HyperPod with K8s GPU device plugin scheduling.
