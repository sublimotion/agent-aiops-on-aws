## Elevation rationale

### Lesson #2 and #3: HyperPod tolerations and disk-pressure taint
These are **platform constraints** that apply to ALL HyperPod EKS deployments, not just Gemma 4. The disk-pressure taint clearing procedure and the 3-toleration requirement are operational patterns that every HyperPod blueprint will encounter. Elevating to tech-stack.md prevents rediscovering these issues in future HyperPod deployments.

### Lesson #6: head_dim heterogeneity forces TRITON_ATTN backend
While discovered during Gemma 4 deployment, this is a **framework constraint** for ANY model with heterogeneous head dimensions (256/512 mix), not specific to Gemma 4. The existing rule "Hybrid DeltaNet+GQA models require triton attention backend on Blackwell" covers a different architectural pattern (hybrid attention architectures). This new rule covers head_dim heterogeneity across attention heads, which is a distinct trigger for the TRITON_ATTN requirement.

### Lessons kept local
- Lesson #1, #4, #6, #7: Model-specific details (image tag, tool calling behavior, gating status, benchmark performance) are captured in mdc learn commands for future gemma-4-E4B deployments.
- Lesson #5: kubeconfig context switching is an operational detail about kubectl behavior in multi-cluster environments, not an architectural constraint that deserves a steering rule.
