## Observations for future blueprint iterations

### EFA device plugin pattern

The p5en.48xlarge EFA device plugin failure ("No valid EFA devices found") has now appeared in multiple blueprints (kimi-k2.5, qwen3-next). This may warrant investigation:

1. Is EFA hardware present but drivers not installed?
2. Does p5en require a specific AMI or kernel module?
3. Is this a known limitation of p5en vs p5e instances?

**Recommendation**: Create a dedicated investigation task to test EFA on p5en instances with different AMIs/driver configurations. If EFA is not available on p5en, document this as a known limitation.

### Docker Hub vs ECR staging

This blueprint successfully used Docker Hub images directly (vllm/vllm-openai:qwen3_5-x86_64-cu130) without ECR staging. The readiness audit noted this works because NAT gateway is enabled, but may cause rate limiting issues.

**Recommendation**: Consider adding guidance on when to use Docker Hub directly vs ECR staging:
- ECR staging: production workloads, repeated pulls, cost-sensitive (NAT gateway costs)
- Docker Hub direct: one-off benchmarks, prototyping, when images aren't available in ECR

### Model architecture validation workflow

The FP8 TP=8 compatibility issue was discovered after infrastructure deployment and capacity block reservation. This wasted approximately 30 minutes of GPU time during troubleshooting and fallback to TP=4.

**Recommendation**: Add a pre-flight validation stage that tests model loading with different TP settings on a CPU-only or small GPU instance before reserving capacity blocks. The elevated steering rule captures the principle; implementation could be a bash script that attempts model loads with various TP settings and validates they don't error.
