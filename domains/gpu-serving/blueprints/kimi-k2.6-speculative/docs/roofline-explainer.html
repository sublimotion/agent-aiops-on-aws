Pareto frontier = the curve connecting the best achievable configurations. The measured story is more nuanced than the pre-experiment projection: EAGLE3 shifts the frontier outward at c ≤ 256 (peak 8,179 tok/s @ c=256 with TP4+DP2), but loses to vLLM baseline at c=512 (7,759 vs 10,437). Pareto Frontier vs Theoretical Limit

Why Pareto is the right comparison

Theoretical Limit

The absolute max if ALL hardware was 100% utilized. For K2.6 on B300: ~1.7M tok/s. Not achievable — you'd need batch=1.7M sequences decoding simultaneously, which is physically impossible (memory, scheduling, serial token generation).

Useless as an optimization target.

Pareto Frontier

The best achievable (latency, throughput) pairs given real-world constraints. At each concurrency level, it's the optimal configuration. Measurable — sweep all configs and plot the outer envelope.

This is your optimization target.

Key Difference

The theoretical limit says "your hardware could do 1.7M tok/s" — but that's like saying a car engine could output 500HP if it had no friction, cooling, or transmission. The Pareto frontier says "given real physics, the fastest you can go at this load level is X." Optimization means pushing the frontier outward, not chasing an impossible number.

Multi-Node Decision Rule

Disaggregation (P/D split, remote KV): Only when KV cache memory is exhausted AND sessions have long idle periods. For K2.6 agentic: NOT needed — 1,500 GB KV budget handles 256+ sessions at 128K.

Horizontal replicas: When QPS exceeds single-node saturation (~20 req/s). This is simple load balancing, not disagg — each replica is independent.

The BW wall is NOT solvable by multi-node. Adding nodes doesn't increase per-node bandwidth. The only lever is speculative decode (more tokens per BW-limited step) or model compression (fewer bytes to read per step).

Right-Sizing Verdict

The idle 80% compute is an inherent property of autoregressive decoding — it's true on every GPU, at every scale, for every LLM. It's not over-provisioning; it's the nature of the workload (low arithmetic intensity at decode).

You can't buy less compute with same BW — GPU silicon bundles them together. The BW/FLOP ratio varies only ~1.5x across SKUs.

The actionable right-sizing moves are:
1. EAGLE3 — converts idle FLOPs into useful draft verification (~20% → 35% utilization)
2. Quantize further — INT4 → INT3/INT2 reduces bytes-to-read, making each BW-limited step faster
3. Smaller instance IF cost/tok matters more than peak tok/s — H200 is 35% cheaper, K2.6 fits, but 40% less throughput
4. Accept the waste — for latency-sensitive agentic workloads, you're paying for BW and getting compute "free"

The Punchline (updated with measured data)

EAGLE3 on a single B300 node gives 4.0× faster per-token decode for agentic workloads (302 vs 76 tok/s at c=1) — the real value is UX, not bulk cost. For high-QPS API serving, plain vLLM TP8 + prefix caching wins on unit economics ($0.43/M). For interactive agents, the 4× decode speedup is worth the slight $/tok premium. At typical enterprise scale (10-200 coding agents), a single node handles everything. Disagg, fleet routing, and EP across nodes are relevant only at inference-provider scale. Route by workload type before adding multi-node complexity.

The Punchline

$/M tokens varies 1,875x across options ($0.04 → $75). But true cost only varies 2.5x ($5.01 → $12.50). Human intervention cost dominates. Optimizing pass rate from 50% → 80% saves more than any infra optimization. K2.6 wins because it has API-tier intelligence at self-hosted cost.

What This Means for Infra Decisions

EAGLE3 on B200 reduces $/task by 60% vs baseline — but true cost barely changes ($5.01 vs $5.02). Infra optimization matters for budget (total monthly spend) not for per-task economics. The real value of cheaper infra: you can run MORE tasks within the same budget, increasing total developer productivity.
