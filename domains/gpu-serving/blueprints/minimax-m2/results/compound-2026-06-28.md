## Elevated to steering

### 1. Context-pinning for destructive automation
**Rule**: When running detached infra scripts that scale nodes or terminate instances, NEVER rely on ambient kubectl context. Pin it explicitly in every kubectl call, and gate any destructive action (scaledown, terminate) behind a positive confirmation that you are operating the intended cluster.

**Target**: `.claude/steering/tech-stack.md` → GPU Serving Conventions → Deployment Conventions

**Justification**: Kubectl context drift sent a trap-scaledown at the wrong cluster (us-west-2 vs us-east-2), terminating a live B200. Lost ~60min rebuild. Cross-cutting operational rule; applies to any unattended runner with destructive actions.

### 2. vLLM cache-hit counter is server-side only (not per-request)
**Rule**: vLLM 0.19.x–0.23.x reports prefix cache hits in SERVER COUNTERS (`vllm:prefix_cache_hits_total`) on the `/metrics` endpoint, NOT in the per-request `cached_tokens` field (which returns None on these builds). Client-side cache-hit measurement reads 0; you must harvest the Prometheus counter before/after the batch.

**Target**: `.claude/steering/tech-stack.md` → GPU Serving Conventions → Benchmark / observability

**Justification**: Recurred 3× this session (early bench.py, then Prometheus harvest plumbing). The per-request field exists in the API spec but is not populated by this engine version. Cross-cutting observability pattern; affects any vLLM benchmark that measures cache hit rate.

### 3. Observability pod is a load-bearing harvest dependency
**Rule**: Before trusting any cache-hit or KV-utilization measurement from Prometheus, verify the observability pod (Prometheus scraper) exists and is scraping the serving pod. A "cache=0" reading with no scraper running is an instrumentation gap, not a cache miss.

**Target**: `.claude/steering/tech-stack.md` → GPU Serving Conventions → Benchmark / observability

**Justification**: Early plumbing returned cache=0 because the Prometheus pod wasn't running yet. This is a validation-before-assert pattern from `benchmark-analysis.md`.

### 4. validate the OUTPUT artifact, not just exit code
**Rule**: A runner exiting rc=0 does NOT mean it produced its deliverable. After any unattended run, validate the output artifact exists and is non-empty (e.g., open the JSON, check its structure) before trusting the "success" signal. Prefer an append-only ledger + rebuild-at-end so a single bad incremental write can't zero the deliverable.

**Target**: `.claude/steering/tech-stack.md` → GPU Serving Conventions → Benchmark / runner patterns

**Justification**: The heredoc + json.load(sys.stdin) bug silently zeroed the pareto output despite rc=0. The VALIDATE_ONLY run caught it before the full grid. Meta-lesson: output validation is orthogonal to exit-code checks.

#### 1. Context-pinning for destructive automation (after L93)

#### Pin kubectl context explicitly in unattended runners with destructive actions

When running detached scripts that scale nodes (`aws eks update-nodegroup-config ... desiredSize=0`) or terminate instances, NEVER rely on ambient `kubectl` context. Pin the context explicitly in every kubectl call and gate any destructive action behind a positive confirmation that you are operating the intended cluster.

```bash
# Pattern: context-pinned kubectl
KCTX=(kubectl --context "$EXPECT_CONTEXT")
"${KCTX[@]}" get nodes

# Preflight before any scaledown
if ! "${KCTX[@]}" get nodes -l blueprint=<name> | grep -q Ready; then
  echo "ERROR: Expected node not Ready in context $EXPECT_CONTEXT"
  exit 1
fi
PREFLIGHT_OK=true

# Scaledown gate
if [[ "$PREFLIGHT_OK" == "true" ]]; then
  aws eks update-nodegroup-config ... --desired-size 0
fi
```

Lost ~60min rebuild. Context-pinning + preflight interlock prevents the wrong-cluster trap from executing.

#### 2. vLLM cache-hit counter is server-side only (after benchmark section)
Added under § GPU Serving Conventions → Benchmark / observability:

```markdown
#### vLLM cache-hit measurement is server-side only (Prometheus counters), not per-request
<!-- stack: vllm=0.19.1rc1-0.23.0 | validated: 2026-06-27 -->

vLLM 0.19.x through 0.23.x reports prefix cache hits in **SERVER COUNTERS** on the `/metrics` endpoint (`vllm:prefix_cache_hits_total`, `vllm:prefix_cache_queries_total`), NOT in the per-request response's `cached_tokens` field (which returns `None` on these builds). Client-side cache-hit measurement reads 0; you must harvest the Prometheus counter snapshot before/after the batch to compute the delta.

```python
# WRONG (reads 0 on vLLM 0.19-0.23)
cached_tokens = response.usage.cached_tokens  # None

# RIGHT
# Snapshot Prometheus vllm:prefix_cache_hits_total before/after batch, take delta
hit_rate = (hits_after - hits_before) / (queries_after - queries_before)
```

The per-request `cached_tokens` field exists in the OpenAI API spec but is not populated by these engine versions. Verify the observability pod (Prometheus scraper) is running and scraping before trusting a "cache=0" reading — a missing scraper is an instrumentation gap, not a cache miss.
```

#### 4. Output artifact validation, not just exit code (new rule after benchmark section)
Added under § GPU Serving Conventions → Benchmark / runner patterns:

```markdown
#### Always validate the output artifact, not just the exit code

A runner exiting `rc=0` does NOT mean it produced its deliverable. After any unattended run, validate the output artifact exists and is non-empty before trusting the "success" signal.

```bash
# WRONG — trusting exit code alone
if ./run-benchmark.sh; then
  echo "Success"
fi

# RIGHT — validate the artifact
if ./run-benchmark.sh && [[ -s results/pareto.json ]] && jq empty results/pareto.json 2>/dev/null; then
  echo "Success — artifact validated"
else
  echo "FAILED — missing or invalid output"
fi
```

Prefer an **append-only ledger + rebuild-at-end** pattern: write results to a `.jsonl` as they're produced, then rebuild the headline artifact from the ledger at the end. A single bad incremental write can't zero the deliverable.

**Why**: 2026-06-27, minimax-m2 VALIDATE_ONLY run completed `rc=0` with real per-config data in the trajectory ledger, but the headline `pareto-<date>.json` was `[]`. Root cause: `python3 - <<'HEREDOC' ... json.load(sys.stdin)` — the heredoc redirected stdin, so `json.load(sys.stdin)` parsed the consumed script text → `JSONDecodeError` → point never appended. The trajectory survived only because it used `>>` append (no stdin conflict). The JSONDecodeError tracebacks in the log were mis-attributable. Only validating the pareto artifact caught it before the full grid.
```
