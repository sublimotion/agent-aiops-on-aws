Why the L4 numbers aren't here. The spec prefers g6.xlarge (L4 24GB, ~$0.80/hr). Voxtral-Mini-3B BF16 (~9.5 GB) fits comfortably in L4's 24 GB. L40S has ~3× FP16 TFLOPs and 2× VRAM, so per-stream RTFx is an upper bound; cost-efficiency projects ~2.1× better on L4 (per spec: ~75% throughput × ~57% $/hr). Run the same transcription sweep on g6.xlarge before quoting an L4 cost externally.

Concurrency scaling · aggregate vs per-stream RTFx

Sweep levels c = [1, 4, 16] · 5 warmup + 30 steady per level · round-robin 3s / 10s / 30s WAV chirps. Aggregate RTFx (audio-s processed / wall-s) climbs with concurrency; per-stream RTFx p50 peaks at c=4 then degrades as queueing kicks in.

Aggregate RTFx (line, left) and per-stream RTFx p50 (line, right) vs concurrency

Trade-off shape. For batch transcription, c=16 maxes throughput at 482× aggregate RTFx. For interactive/real-time use cases where per-stream latency matters, c=4 is the sweet spot — RTFx p50 87× (wall p50 127 ms) vs RTFx p50 41× at c=16 (wall p50 346 ms). At c=1 the GPU is under-utilized: aggregate RTFx is only 85× even though per-stream is 95×.

Short utterances are cost-poor. The 30 s bucket delivers 1,481 audio-min/$, which is 6.4× more cost-efficient than the 3 s bucket (232 audio-min/$). Even though 3 s clips finish faster in absolute terms (wall p50 202 ms vs 523 ms), each request pays the same fixed per-request overhead (HTTP + Mel encoder warm-up + scheduler admit). Amortising that overhead over 30 s of audio is roughly an order of magnitude better. Actionable: for contact-centre or voice-mail workloads where utterances are naturally short, batch consecutive turns into a single transcription call where the API allows, or accept 6× higher unit cost.

API surfaces · both registered and verified

POST /v1/audio/transcriptions

OpenAI Whisper-compat. Multipart upload of an audio file. Returns a single JSON with {"text": "..."}. Used for the perf sweep.

curl -F "file=@audio.wav" -F "model=voxtral" \
  http://svc/v1/audio/transcriptions

Streaming: waits for full audio before emitting tokens. Not frame-streaming.

POST /v1/chat/completions (audio_url)

Mirror of the image_url shape — not the older {"type":"audio","path":...} form in the Mistral docs / spec narrative. SSE token streaming works as standard.

{"role":"user","content":[
  {"type":"text","text":"Summarize the audio."},
  {"type":"audio_url","audio_url":{
     "url":"data:audio/wav;base64,..."}}
]}

Streaming: token-level SSE works.

True frame-streaming requires the Realtime variant. Both endpoints above consume the full audio before token generation begins. For sub-second time-to-first-word on long-form audio, deploy Voxtral-Mini-4B-Realtime-2602 behind /v1/realtime WebSocket — out of scope for this artifact.
