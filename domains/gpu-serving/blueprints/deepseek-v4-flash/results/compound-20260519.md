## Lessons elevated to steering

The following cross-cutting findings were promoted from `lessons.md` to `.claude/steering/tech-stack.md` because they apply broadly beyond DeepSeek V4 Flash.

### 1. EKS managed nodegroups don't auto-label `nvidia.com/gpu.present=true`

**Where**: `.claude/steering/tech-stack.md` → new rule under "GPU Serving Conventions → Deployment Conventions"
**Source**: lessons.md HIGH #3 ("EKS managed nodegroups don't auto-label...")
**Why elevate**: applies to every EKS-managed GPU nodegroup the repo will ever launch (already has gemma4-hyperpod, qwen3-235b-b300, glm5-llmd, etc.) — not DSv4-specific. Verified specifically on `aws eks create-nodegroup` with `AL2023_x86_64_NVIDIA` AMI; eksctl does this automatically.

### 2. Speculative decoding < 60% acceptance is a net throughput LOSS

**Where**: `.claude/steering/tech-stack.md` → new rule with version tag `<!-- stack: vllm>=0.20, mtp/eagle/ngram | validated: 2026-05-19 -->`
**Source**: lessons.md MEDIUM #11 ("MTP speculative decoding hurts...")
**Why elevate**: this is a **class of finding**, not DSv4-specific. Same physics applies to Gemma 4 MTP (#41789 reported 0.2% acceptance), Qwen3 EAGLE, future spec-decode methods. The rule mandates a pre-promotion check using `vllm:spec_decode_num_accepted_tokens_total / vllm:spec_decode_num_drafts_total` and explicitly warns against synthetic-only validation (links to the existing `feedback_synthetic_specdec_repetition.md` memory).

### 3. Standard model staging pattern (RAID0 + S3-cached HF download)

**Where**: `.claude/steering/tech-stack.md` → new rule with version tag `<!-- stack: huggingface_hub>=0.24, hf-cli<1.15 OR snapshot_download API | validated: 2026-05-19 -->`
**Source**: lessons.md MEDIUM #4 ("`huggingface_hub` v1.15+...") + memory `feedback_model_staging_pattern.md`
**Why elevate**: every future blueprint needs this. Codifies the canonical pattern (init-nvme → S3-cached download → persist-back), the gotchas (`hf` CLI v1.15 broken `--exclude`, deprecated `HF_HUB_ENABLE_HF_TRANSFER`, Xet replacement), and points at the canonical reference implementation in `domains/gpu-serving/blueprints/deepseek-v4-flash/k8s/`.

### 4. Co-tenant GPU-tolerant pods can claim freshly-launched expensive nodegroup GPUs

**Where**: `.claude/steering/tech-stack.md` → new rule (no version tag — broadly applicable)
**Source**: lessons.md MEDIUM #5 ("Stale Ray workers from a different blueprint claimed B300 GPUs")
**Why elevate**: this is an EKS multi-tenancy gotcha that applies to *any* shared cluster. Includes a concrete `kubectl ... | jq` snippet to detect the case before launching expensive capacity. Affects gemma4-hyperpod, glm5-llmd, llmd-hyperpod, kimi-k2.6 — anything sharing a cluster with another GPU workload.

### 5. (Augmentation) IMDS hop-limit rule extended

**Where**: `.claude/steering/tech-stack.md` → existing IMDS rule, appended note
**Source**: lessons.md HIGH #2 ("EKS managed nodegroup IMDSv2 hop limit defaults to 1...")
**Why augment vs new**: the existing rule covers Ray Serve specifically; the V4 Flash run validated it on B300 with non-Ray workloads and identified the specific managed-nodegroup constraint (can't be set via launch template `metadata_options`, only post-launch `modify-instance-metadata-options`). Added that detail in-place.
