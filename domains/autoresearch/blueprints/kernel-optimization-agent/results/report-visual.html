Decision Tree: Which Parallelism Strategy?

Does the model fit on one node?
YES (K2.6: 961GB < 1,128GB) → Use TP
NO → EP or Pipeline Parallelism required
Is latency critical (chatbot, <50ms ITL)?
YES → Replicas (TP8 x N nodes). Linear scaling, no dispatch overhead
NO (throughput-only) → Still replicas for short context
Is context very long (64K+) with many concurrent users?
YES → Replicas + KV offload (HiCache: 3.5TB NVMe per node)
NO → Simple replicas
Multi-node prefill farm (latency-tolerant)?
YES → EP on prefill nodes + TP on decode nodes (DeepSeek architecture)

Key Takeaways

1. Configuration > Kernel Engineering
The actionable gain (~2.5x) comes from model-specific MoE tile tuning via --tune-gemm-by-model. CUDA graphs (default ON) eliminate scheduling overhead. Custom kernel development yielded <5% on top of this.
2. MLA Decode Is at Hardware Ceiling
122% BW utilization with L2 amplification. No kernel rewrite can improve it. Only reducing data movement helps (shorter context, quantized KV, speculative decode).
3. Flat Routing (n_group=1) Makes MoE Optimization Extremely Hard
384 experts with uniform traffic = no hot-set, no grouping structure, no weight reuse at decode. This is an architectural choice that trades kernel efficiency for model quality.
4. EP Is a Model-Size Play, Not a Serving Optimization
On single node where the model fits, replicas always win. EP's dispatch cost exceeds any benefit from larger GEMMs for K2.6's flat routing.
5. vLLM's Existing Stack Is Near-Optimal
fused_moe + CUDA graphs + DeepGEMM E8M0 + FlashInfer MLA = already at or near hardware limits for this architecture class. Focus on deployment config, not kernel development.
