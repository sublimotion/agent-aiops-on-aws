The one-sentence thesis
The kernel is fine. The configuration point chosen for it on your shape and your GPU is often 1.5–3× off peak — and because the cost surface has discrete cliffs that no formula models, the only way to find the good point is to measure a grid of candidates.

1 · A tile config is a point in a discrete space

A tiled GEMM (the matmul at the heart of every FFN and MoE expert) is parameterized by a handful of integers. The kernel author writes the algorithm once; the config picks how it tiles the problem:

BLOCK_M · output rows per tile BLOCK_N · output cols per tile BLOCK_K · reduction depth per step GROUP_M · L2-locality scheduling num_stages · software-pipeline depth num_warps · threads per CTA split_K · partition the reduction

In vLLM/SGLang this is literally a JSON file. Below is the exact artifact this blueprint had to create — it did not exist for the H200 + 384-expert combination, and its absence cost 23% throughput:

// E=384,N=256,device_name=NVIDIA_H200,dtype=fp8_w8a8,block_shape=[128,128].json
{
  "1":  {"BLOCK_SIZE_M": 16, "BLOCK_SIZE_N": 128, "BLOCK_SIZE_K": 128,
         "GROUP_SIZE_M": 1, "num_warps": 4, "num_stages": 3},
  "8":  {"BLOCK_SIZE_M": 16, ...},      // a different tile per token-count bucket
  "128":{"BLOCK_SIZE_M": 64, ...}
}

2 · Why there is no closed-form "best tile"

The optimum is the point that satisfies four objectives at once, and the first two pull in opposite directions:

↑ Bigger tiles
Higher arithmetic intensity per tile → tensor cores stay fed → saturate compute. More data reuse per byte loaded.
⚔︎
↓ Smaller tiles
Working set + num_stages pipeline buffers must fit in ~228 KB SRAM and the register file. Spill → occupancy collapse.

Objective 3 · Occupancy

Enough concurrent CTAs must be resident to hide memory latency. num_warps, num_stages, and register pressure all gate this. One extra stage can spill registers and halve the warps the SM can hold.

Objective 4 · Even tiling

If M % BLOCK_M ≠ 0 the last "remainder wave" runs partly-empty tiles. With small M (MoE decode!) a single wasted wave can be a large fraction of total work.

The cost surface is cliffed, not smooth
You cannot interpolate. Adding one pipeline stage doesn't make things "a little slower" — it can trip a register-spill threshold and drop throughput off a cliff. Because the cliffs depend on the compiler's register allocation and the scheduler's behavior (not analytically modelable), the only reliable signal is a measured benchmark.

3 · Why MoE breaks every shortcut a dense GEMM enjoys

A dense LLM tunes one GEMM shape and reuses it forever. MoE violates each assumption that makes "tune once" work:

PropertyDense GEMMMoE — why tuning is harder
Effective M Huge (8K+ at prefill), insensitive to tile choice tiny Each expert sees only tokens·top_k / n_experts rows — tens to low hundreds. Small-M is exactly where tile choice dominates.
M stability Static, known ahead of time data-dependent Routing is dynamic; per-expert counts shift every batch and are load-imbalanced (hot vs cold experts). One static tile can't be optimal across the range.
Regime spread One operating point two+ Decode (M≈batch, memory-bound) wants a different tile than prefill (M in thousands, compute-bound). Hence per-M-bucket configs in the JSON.
Launch shape One big GEMM grouped Grouped/segmented GEMM packs variable-sized expert segments into one launch; GROUP_M↔CTA mapping interacts with tile shape in ways that don't transfer from the dense case.
GEMMs per layer Effectively one shape two shapes gate/up and down projections have different N/K → want different tiles, and the SiLU·mul fusion between them changes the SRAM budget.
FP8 block scaling Often FP16, no constraint coupled Fine-grained FP8 needs block_n=128; the scale-block granularity couples to BLOCK_N and shrinks the valid search space to non-obvious survivors.
The FP8 constraint you already hit
The rule moe_intermediate_size / TP % 128 == 0 from the B200/B300 deployments is exactly a tiling constraint surfacing at the config level — the FP8 block boundary (block_n=128) dictating which tile widths are even legal. Tile tuning and FP8 layout are the same problem viewed from two angles.

5 · The universal thing isn't a kernel — it's the loop

If every shape, dtype, GPU, and attention variant needs its own tuned config, is there anything universal left? Yes — but it moved up a level. The durable artifact is the method, not any single kernel.

FlashAttention is the proof, not the counterexample

FlashAttention feels like the universal kernel that beat tuning. It isn't. What generalized was the algorithm — IO-awareness: tile the attention, keep the softmax online, never materialize the N×N matrix in HBM. What did not generalize was the implementation:

GenerationWhy a rewrite was forced
FA2 → FA3Near-total rewrite for Hopper: TMA, warp specialization, FP8 via wgmma
FA3 → BlackwellRe-specialize again for SM103 (TCGEN5, new SRAM/register budget)
Full attn → MLAFlashMLA — KV is a 576-dim latent, not full heads; different kernel entirely
The real axis isn't "universal vs not"
It's which layer generalizes. The algorithm (IO-aware tiling, grouped GEMM, online softmax) is durable and transfers everywhere. The kernel is disposable — it re-specializes per hardware generation and per attention variant. MoE just sits further toward the disposable end, because its problem shape is dynamic and tiny, so even the per-shape config doesn't hold still.

Hybrid architectures push everything toward per-layer search

A modern model is no longer one attention type. A single layer stack now mixes primitives with different roofline positions, each wanting a different kernel:

GLM-5 · DeepSeek sparse attention (NSA) Qwen3.5 · linear + full attention interleaved Gemma · sliding-window + full per-layer SSM hybrids · Mamba blocks in the stack

There is no single fused megakernel optimal across a stack mixing NSA + full + linear attention. You need a portfolio of specialized kernels plus a scheduler that dispatches the right one per layer — and the autotuning surface grows combinatorially with every new primitive. "One universal optimization" is gone for good.

This procedure is shape-, model-, and hardware-agnostic — it is the loop this blueprint runs (it maps directly onto States 0→5 of generate-candidate plus the freeze manager). The K2.6 run is the proof in both directions:

The search finds wins formulas can't
The +23% wasn't a clever kernel — it was the search finding a config (E=384,N=256,H200) that simply didn't exist yet. The procedure surfaced it; no formula would have.
Knowing when to STOP is half the method
MLA decode profiled at >100% BW util (L2-amplified) — already at the hardware ceiling. A "negative" result is just as valuable: the loop tells you to stop searching that layer and redirect (here, to CUDA-graph capture: +14.9×, a scheduling win, not a kernel at all).
Why this is built as an agent, not a kernel
Optimization is fragmenting — per-layer, per-architecture, per-SKU — faster than any human can hand-tune. The response isn't a better kernel; it's making the search itself cheap and automatic. That's the entire bet behind this blueprint, and behind commercial plays (Wafer.ai) running the same profile→diagnose→patch→verify loop as a service.

So: is it "along the same lines"?
Yes in spirit — both are pure utilization wins that leave the model untouched, and both exploit hardware concurrency the naïve path leaves idle. But they're complementary, not the same lever. Synthesia overlaps compute with data movement (a Real-Time-Factor / pipeline problem, and notably their kernel was the unoptimized Diffusers model — they explicitly note compilation would stack on top). Tile tuning makes the compute itself denser. On a generative-video stack you'd want both; on K2.6 serving, tile tuning is the in-kernel half and CUDA-graph capture (the +14.9× decode win in this blueprint) is the scheduling half — the direct analogue of Synthesia's contribution.
