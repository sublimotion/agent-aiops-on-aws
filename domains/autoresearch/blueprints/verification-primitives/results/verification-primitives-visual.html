Key Insights

Two-stage checkpoint solves Parkinson's Law
Edit@40% + Verify@55% shifts first tool use from 67% → 54% of budget. full_pipeline becomes the dominant pattern at 45% (up from 8%). Fix rate: 95% (+30pp). Gold pass: 24% (+10pp, p=0.0009).
Separate edit nudge from verify nudge
The key design insight: checkpoint at 40% breaks Parkinson's Law ("make your edit now"), checkpoint at 55% creates a verify window ("test and review your patch"). Two messages, +16% cost, +30pp fix rate, +10pp gold pass.
Stronger models compose more richly
Sonnet adopts tools 3.2x more than Haiku, uses 4 distinct patterns (vs 3), discovers the full_pipeline_iterate pattern, and gets all gold passes from tool users. Verification primitives amplify model capability.
Composition is adaptive, not cloned
No single pattern dominates (max 45% concentration). Agents vary strategy by issue — this is Level 3 verification (primitive composition with judgment), not Level 2 (behavioral cloning).
Agents never discover TDD independently
Without checkpoint injection, 0% tool adoption across all unguided cells. Parkinson's Law dominates — agents explore exhaustively before editing. The two-stage design engineers early verification without mandating it.
Emergent patterns match engineered pipelines
The full_pipeline pattern (gen→run→review) is structurally similar to InfCode's 3-agent pipeline. Two-stage checkpoints close the timing gap — agents now verify at 54% of budget, not 67%.

Research Question

Core Hypothesis

Agents given verification primitives as callable tools will discover effective verification patterns (front-loaded testing, adversarial review before submission) that improve pass rate, without human-engineered orchestration. The composition is learned, not designed.

Motivation

CoderForge's 413K-trajectory analysis found that early test fraction is the single strongest predictor of agent success (56.3% concordance). But those agents only had access to existing repo tests. What happens when you give agents the ability to generate their own verification? This extends the verification spectrum from "run existing tests" (hard verifier) to "create then run tests" (skill-to-hard composition).

Counter-Evidence Addressed

arXiv:2602.07900 found that ad-hoc test writing during issue resolution has marginal utility. Agents prefer print statements over formal assertions. Our hypothesis: this fails because casual test writing is confirmatory. Adversarial test generation ("write tests designed to break your patch") should produce qualitatively different results — same as our v009 finding that adversarial framing beats confirmatory by 2.3x.

Verification Primitives (3 Tools)

generate_tests

LLM-generated test suites via Bedrock Haiku
Input: problem statement + current patch diff + source files
Output: pytest test file content
Modes: confirmatory ("verify this fix works") vs adversarial ("break this patch")
Cost: ~$0.008/call   Latency: 7-10s
Key design: Agent-facing description is helper-framed ("validate your fix"). Adversarial framing lives inside the tool's LLM prompt, invisible to the agent.

run_tests

Sandboxed pytest execution in workspace
Input: test file content + workspace (base commit + patch applied)
Output: per-test pass/fail, stdout, stderr
Timeout: 60s per suite
Cost: compute only (~$0.01/run)
Latency: 0.5-5s

adversarial_review

v009 adversarial rubric, single LLM call
Input: problem statement + patch diff + optional test results
Output: structured verdict (likely_correct / likely_incorrect + score 0-1)
Rubric: 5-axis (problem alignment, logic, completeness, scope, test safety)
Cost: ~$0.003/call
Baseline: v009 alone has 0.92 precision, 0.14 recall

Experimental Design

Benchmark

SWE-bench Lite — 300 real GitHub issues across 12 Python repos. Phase 1-4 used a 50-issue stratified subset (seed 42). Phases 5-6 used the full 300-issue set. Repo distribution: Django 38%, sympy 26%, matplotlib 8%, sklearn 8%, pytest 6%, sphinx 5%, others 9%.

Agent Setup

  • Models: Claude Haiku 4.5 (Phase 1-3) and Claude Sonnet 4.6 (Phase 4-6) via AWS Bedrock invoke_model
  • Turn budget: 30 turns (increased from initial 15 after Phase 1 showed insufficient budget)
  • Standard tools: read_file, edit_file, list_dir, search, bash
  • Treatment tools: generate_tests, run_tests, adversarial_review (added to standard set)
  • No forced usage: Tools are available but never required. Agent decides when and whether to invoke them.

Cells

  • Control: Standard tools only, no verification primitives
  • B_checkpoint: Standard tools + all 3 verification primitives + checkpoint injection at 70% of turn budget ("You have N turns remaining. Consider validating your patch before submitting.")
  • B_twostage (Phase 6): Standard tools + all 3 verification primitives + two-stage checkpoint injection: edit nudge at 40% ("make your edit now") + verify nudge at 55% ("run tests and review your patch")

Phase 2 also tested: unguided (tools available, no reminder), mandatory ("You MUST use tools"), and TDD-first (7-step workflow). Checkpoint injection outperformed all variants. Phase 6 introduced two-stage checkpoints to directly address Parkinson's Law by separating the "edit" and "verify" nudges.

Guidance: Checkpoint Injection

Single checkpoint (B_checkpoint): At turn 21 of 30 (70% of budget), the system injects: "You have 9 turns remaining. Before submitting your patch, consider using generate_tests and run_tests to validate your changes, and adversarial_review for a final check."

Two-stage checkpoint (B_twostage, Phase 6): Two separate injections: (1) Edit nudge at 40% (turn 12): "You've explored enough — make your edit now." (2) Verify nudge at 55% (turn 17): "Run generate_tests and run_tests on your patch, then adversarial_review." This separates the "stop exploring" signal from the "start verifying" signal, directly targeting Parkinson's Law.

Both are light-touch guidance. Stronger guidance (mandatory language, TDD workflow) either reduced fix rate or had zero adoption. Two-stage proved most effective: 95% fix rate, 83% adoption, 24.3% gold pass (p=0.0009 vs control).

Two-Layer Framing (Phase 5-6 Discovery)

Tool descriptions have two audiences:

  • Agent-facing (decides to call): Helper-framed — "Validate your fix by generating edge-case tests. Catches issues before submission."
  • Inner LLM (executes tool): Adversarial-framed — "Write tests designed to break this patch. Target boundaries and assumptions."

Phase 5 tested helper vs adversarial agent-facing descriptions. Result: no difference (59% vs 58% adoption). Parkinson's Law, not framing, drives voluntary adoption.

Evaluation

Metrics

  • Fix rate: % of issues where the agent produces any patch (edit_file called with non-empty diff)
  • Gold pass rate: % of issues where the agent's patch passes the gold FAIL_TO_PASS tests from SWE-bench (the ground-truth correctness metric)
  • Precision: gold pass / fix rate — of patches produced, what fraction are actually correct
  • Tool adoption: % of issues where agent invoked any verification primitive
  • Tool timing: First tool call as % of turn budget (lower = earlier = better)
  • Composition pattern: Classified from tool invocation sequences (5 patterns, see Results tab)

Gold Evaluation Procedure

  • Clone repo at base_commit from SWE-bench
  • Apply gold test_patch (adds the FAIL_TO_PASS test cases)
  • Apply agent's diff on top
  • Create Python 3.12 venv with setuptools + repo dependencies (pip install -e .)
  • Run the FAIL_TO_PASS test command. Return code 0 = pass.
  • Cleanup workspace between issues

Limitation: Gold eval runs without Docker. Some repos (scikit-learn, matplotlib) need C compilation that may fail. Pass rate is a lower bound.

Statistical Testing

All comparisons use Fisher's exact test (two-sided) on 2x2 contingency tables (pass/fail x control/treatment). Significance threshold: p < 0.05. No multiple-comparison correction applied (each phase tests a single primary hypothesis).

Composition Pattern Classification

Pattern Taxonomy

Patterns are classified from the sequence of verification tool calls in each agent trajectory:

  • ignore: No verification tools called
  • generate_run: generate_tests followed by run_tests (1 cycle)
  • generate_run_iterate: generate_tests → run_tests with 2+ cycles (retry on failure)
  • full_pipeline: generate_tests → run_tests → adversarial_review (1 cycle)
  • full_pipeline_iterate: Full pipeline with 2+ cycles

Classification is deterministic based on tool call presence: if adversarial_review was called, it's a full_pipeline variant. If multiple generate/run cycles exist, it's an iterate variant.

Verification Levels (Framework Context)

  • Level 1 — Tool competence: Model can call pytest, format tool calls. Baseline capability.
  • Level 2 — Behavioral cloning: Model replicates successful trajectory patterns (Nebius RFT, SERA SVG). Pattern replication, not judgment.
  • Level 3 — Primitive composition (this experiment): Model composes verification primitives with judgment — when, what kind, how much. Contextually adaptive strategies.
  • Level 4 — Absorbed verification: Model generates verified-quality output without external tools (RL with calibrated verifier reward).

This experiment measures whether agents reach Level 3. Evidence: adaptive pattern selection (no single dominant pattern, max 45% concentration with two-stage) suggests Level 3 for Sonnet. The two-stage checkpoint shifts the dominant pattern from ignore to full_pipeline, indicating richer composition when Parkinson's Law is broken.

Limitations & Threats to Validity

No Docker isolation
Gold eval runs in local venvs. Some repos (scikit-learn C extensions, matplotlib) may fail to build. Pass rates are lower bounds. SWE-bench's official Docker eval would yield higher absolute numbers.
Single model family
Only Claude models tested (Haiku 4.5, Sonnet 4.6). Results may not transfer to GPT-4, Qwen, or open-source models. The adversarial review rubric (v009) is calibrated for Claude.
No multiple-comparison correction
Each phase tests one primary hypothesis, but the full experiment tested many variants. The Phase 4 p=0.028 would not survive Bonferroni correction across all tested cells.
50-issue subset bias
The stratified 50-issue subset used in Phases 1-4 was biased toward easier issues. Fix rate dropped from 88% to 77% when scaled to 300 issues in Phase 5. Phase 6 confirmed the pattern holds at scale: two-stage achieves 95% fix on 300 issues.
Checkpoint injection confound
The checkpoint reminder may improve fix rate by simply reminding the agent to finish editing (reducing abandonment), independent of verification tools. Phase 6's two-stage design partially addresses this: the edit nudge at 40% is tool-agnostic, while the verify nudge at 55% is tool-specific. The +30pp fix rate gain includes both effects.
Gold pass significance varies by cell
Phase 5's single checkpoint at n=300 showed +4.7pp gold pass (p=0.15, not significant). Phase 6's two-stage checkpoint achieved +10.3pp (p=0.0009, significant). The stronger intervention produces a statistically significant effect; the weaker one does not.
