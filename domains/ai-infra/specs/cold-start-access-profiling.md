# Spec F — Cold-Start File-Access Profiling

## Status: DRAFT

## Hypothesis

For a typical vLLM serving cold start (Python startup → vLLM imports → CUDA init → model metadata read, *excluding* model weights and compile caches), **≤5% of container image bytes are actually read in the first 60 seconds**, and **≥40% of file-system operations are negative lookups** (file-not-found).

## Falsification criteria

Falsified if any of:
- Access ratio (bytes-read / total-image-bytes) > 20% for vLLM cold start.
- Negative-lookup ratio < 15% of total `openat`/`stat` calls.
- The set of touched files varies by >50% across runs of the same image (i.e., access pattern is too unstable to prefetch deterministically).

Any of these would mean lazy loading offers limited advantage over EBS prebake for our workloads, and the lab should pivot Spec A's variant priority accordingly.

## Why this matters

This experiment **runs first** in the lab. Its result determines the variant priority for Spec A (image-pull-acceleration):

- Low access ratio + stable access set → lazy loading + targeted prefetch wins; SOCI/Nydus + FUSE tuning is the dominant variant.
- High access ratio → EBS prebake wins; lazy loading is a marginal improvement.
- Unstable access set → neither lazy nor prebake prefetch helps; we're stuck with default pull or aggressive image shrinking.

It also produces a **deterministic prefetch list** (filenames or globs) that any lazy-loading variant can use to amortize cold-start latency.

## Why this matters

Modal's published datapoint: importing sklearn = ~3,000 stat + ~1,000 openat calls, ~1,000 unique files actually accessed. For an LLM container with millions of files (Python stdlib + PyTorch + CUDA + vLLM + tokenizer assets), the ratio is plausibly far below 5%. If true, lazy loading's ceiling is bounded by access ratio, not bandwidth — making FUSE tuning (Spec E) and prefetch lists the right architectural focus.

## Baseline

The "baseline" here is the *measurement itself* — there's no on/off variant. The experiment establishes ground-truth numbers.

## Measurement

**Tool**: eBPF (`bpftrace` or `bcc`) attached to `openat`, `read`, `stat`, `newfstatat` syscalls, scoped by container PID namespace.

Outputs per run:
- Total bytes read from image filesystem during the window.
- Total file-system operations.
- Negative-lookup count and ratio.
- Per-file access histogram (path, bytes-read, first-access-timestamp).
- Cumulative bytes-touched over wall-clock time.

**Sample size**: 5 runs per cell. Compare access sets via Jaccard similarity to assess stability.

**Output format**: enriched JSON per `standards/benchmark-commons/PROPOSAL.md` plus an `access_set.json` with the touched-file list (for downstream consumption by Spec A's prefetch variants).

## Fixtures

- Existing vLLM containers from `domains/gpu-serving/blueprints/glm5-fp8/` and `kimi-k2.6-speculative/`.
- Vanilla `vllm/vllm-openai:latest` for the unmodified baseline.

No new deployments required. Run on any GPU node; the image content access pattern is what matters.

## Rule the experiment would produce

If hypothesis holds:

> **Cold-start prefetch lists**: For each blessed vLLM container image, ship a `prefetch.txt` (file glob list) generated by Spec F's profiler. Any lazy-loading snapshotter (stargz/SOCI/Nydus) loads the prefetch set eagerly and the rest on demand. Refresh the list whenever the image changes.

If falsified (high access ratio):

> **EBS prebake is the dominant image-pull strategy** for our serving workloads. Skip SOCI/Nydus deployment; invest in Bottlerocket prebake CI.

Either rule is actionable.

## Out of scope

- Model weight files (Spec B's domain).
- Compile caches (Spec C's domain).
- The actual lazy-loading mechanism (Spec A / E).

Negligible. eBPF profiling on existing nodes; no new infrastructure. Estimated < $50 of GPU time across 18 runs.
