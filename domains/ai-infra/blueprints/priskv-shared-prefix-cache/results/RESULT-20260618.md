# PrisKV Shared Prefix Cache — RESULT (FALSIFIED)

**Date:** 2026-06-18 · **Node:** g7e.12xl (2× RTX PRO 6000 Blackwell sm_120, PCIe), Tokyo 1c spot
**Spec:** `domains/ai-infra/specs/priskv-shared-prefix-cache.md` · **Model:** Qwen3-32B-FP8, 2× TP1

## Verdict: FALSIFIED (criterion #1)

> *Falsification #1: "At 70% shared-prefix ratio, PrisKV (Arm C) TTFT improvement over prefix-aware
> routing (Arm B) is <15%."*

Not merely <15% — **PrisKV is 5× SLOWER** than prefix-aware routing at the regime it was supposed to
win. PrisKV adds a host-DRAM KV round-trip that costs more than it ever saves on this hardware.

## Data (70% reuse, TTFT ms)

| Arm | 800-tok p50 | 800-tok p99 | 4000-tok p50 | 4000-tok p99 |
|-----|------------:|------------:|-------------:|-------------:|
| **A** round-robin + local vLLM APC | 49.8 | 168.8 | 63.8 | 894 |
| **B** prefix-aware routing + local APC | **49.3** | **168.7** | **62.8** | 898 |
| **C** PrisKV shared host-DRAM L2 | 102.3 | 410.6 | 314.8 | 2084 |

PrisKV loses at every prefix size, and **gets relatively worse as the prefix grows** (2× slower at
800 tok → 5× slower at 4000 tok) — the opposite of its thesis. Its cached reads (shared-prefix p50)
are 311ms vs B's 63ms on-GPU APC hit.

## Why PrisKV loses (mechanism, measured)

1. **vLLM's local prefix cache (APC) hit is nearly free** — the KV is already in GPU HBM.
2. **PrisKV's hit is a host-DRAM round-trip**: GPU HBM ← (PCIe ~64GB/s) ← host DRAM, via UCX-over-TCP
   + connector serialization. Measured L2 GET ~36ms for 700 tokens; scales with KV size, so a 4000-tok
   prefix's KV (≈10× larger) makes the penalty dominate.
3. **The penalty grows with prefix size**; the benefit (avoided prefill) is small because an 800–4000
   token prefill on a Blackwell GPU is only tens of ms. PrisKV trades a cheap on-GPU recompute for an
   expensive off-GPU fetch.
4. **Bonus finding**: even naive round-robin (A) ties prefix-aware routing (B) at 70%/2-replica —
   with only 2 replicas, round-robin already lands enough requests on a warm-APC replica that smart
   routing adds little. Prefix-aware routing's edge would widen with more replicas / lower reuse, but
   it never needs PrisKV's host hop to capture cross-replica reuse cheaply.

## What this means for the fleet

Confirms the pre-registered skeptical analysis. On PCIe-only g7e (PrisKV's *best-case* hardware —
no NVLink, the scenario the AIBrix blog targets), a shared host-DRAM KV cache is **slower than just
keeping the cache on-GPU and routing to it**. The "zero-copy shared memory" the blog markets did not
even engage (localhost fell back to UCX-over-TCP; `UCX_TLS=sm` timed out). For cross-replica prefix
reuse, **use prefix-aware routing (llm-d / GAIE), not an external KV store.**

## Scope / caveats (honest limits)

- 2 replicas only (quota-capped at g7e.12xl); the multi-replica ZMQ-port collision (L13) was a real
  obstacle even at N=2. Prefix-aware routing's advantage over round-robin would grow at higher N — but
  that only strengthens the "don't need PrisKV" conclusion.
- Single reuse ratio (70%) and moderate sequential load (16–20 sessions). PrisKV's loss is large and
  consistent enough across two prefix sizes that finer sweeps wouldn't flip the verdict; a 0% cell
  would only make PrisKV look worse (pure overhead, no hits).
- Did not hard-stress concurrent writes, so the #41/#42 cache-race bugs weren't exercised; correctness
  was clean under this load.
- Gate #4 (build/serve) PASSED — the stack works; it's just not worth using here. The build took ~14
  undocumented fix-ups (see lessons.md L1–L14), itself evidence against the blog's "turnkey" framing.
