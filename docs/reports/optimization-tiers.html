Optimization Tier Ladder

AI Inference Infrastructure · Tiered Decision Framework · v1 · 2026-06-01

Where does your workload actually belong? 80% of production GPU LLM workloads need only Tier 1 + Tier 2. Roughly 15% need Tier 3 (cold-start) or Tier 4 (routing). Less than 5% need Tier 5 (disagg P/D, request migration, multi-node TP). Reach for Tier 5 before Tier 1 is solid and you are buying complexity you cannot operate.

By the end of this page you will know which tier your workload sits at and what NOT to invest in.

How to read the ladder

The thickness of each top stripe encodes operational complexity, and the bars beneath quantify the cumulative engineering tax. Tier 5 is not "5× better than Tier 1" — it is 5× harder to operate and only pays off on a narrow band of frontier-model workloads. Climbing higher than your workload pattern justifies produces negative ROI: the ranges in this doc are typical, not guarantees.

Tier-by-tier

Five tier cards · what each layer actually does

Each card answers the same five questions: how it works, when to use, when NOT to use, what wins look like, and which lab specs implement it.

Tier 1 — Engine-level defaults

Trivial Always on · zero infra cost

Modern serving engines (vLLM, SGLang, TensorRT-LLM) ship with a small set of feature flags that are strictly Pareto-better than their alternatives but are not always on by default. Chunked prefill splits long prefills into chunks interleaved with decode batches, shrinking request-cost variance the rest of the stack would otherwise have to work around. Continuous batching replaces static-batch padding with token-level batching. Prefix caching hashes shared prompt prefixes and reuses their KV. FP8 halves memory on Blackwell where the MoE TP divisibility rule (moe_intermediate_size / TP % 128 == 0) holds.

When to use
Every workload. There is no exception. Skipping Tier 1 invalidates every higher-tier measurement because you are optimizing on top of an unfair baseline.
When NOT to use
Never — though check FP8 against the MoE divisibility rule before flipping it on, and pin the right TP for your fit (TP=1 wherever possible).
  • Chunked prefill — 2-3× improvement in p99 TTFT under mixed prompt-length workloads (Sarathi-Serve, OSDI '24)
  • Prefix caching — 20-50% prefill saving on multi-turn / shared-system-prompt workloads (Preble)
  • Continuous batching — ~3× throughput vs static batching (Orca / vLLM)
  • FP8 where supported — 2× memory, ~1.5× throughput on Blackwell
  • Right TP — TP=1 wherever weights fit avoids unnecessary NCCL allreduce overhead
Implicit in every blueprint. Methodology gotcha: vendor "5× routing" claims usually have chunked prefill OFF in baseline.

Tier 2 — Production basics

Low Bounded, well-known costs

The minimum viable production deployment: an image small enough to pull in under two minutes, a hardware tuple (driver, AMI, NCCL, engine) that has been seen working before, health-check timeouts wide enough to not kill a JIT-heavy first start, and at least one always-on replica per region. Image-prepull DaemonSets on warm-pool nodes eliminate image-pull from the cold-start path entirely for replicas landing on already-warm nodes.

When to use
Every production workload. If users will be unhappy when it falls over, you are at Tier 2.
When NOT to use
Throwaway dev/test, single-shot batch jobs that tolerate 5-10 min cold start, research notebooks. Everywhere else, this is non-negotiable.
  • Slim image (Spec A) — 1.87× faster image pull (77 s vs 144 s measured, Spec A baselines)
  • Hardware-match pinning — NCCL 2.26.2+ on Blackwell PCIe; AL2023 AMI on B200; FP8 MoE TP rule
  • Health-check tuning — readinessProbe.initialDelaySeconds ≥ 900s for DeepGEMM-heavy stacks
  • Min-1-replica-per-region — codified in warm-node-pool.md
  • Image pre-pull DaemonSet — eliminates image-pull from cold-start for warm-node replicas
Spec A + warm-node-pool steering rule + tech-stack.md hardware tuples. Lessons survive in MEMORY.md.

Tier 3 — Cold-start strategies

Medium Workload-shape dependent

Cold-start is the stage where workload pattern starts dominating the decision. Three composable layers: slim image (Tier 2 already), MX / RunAI streamer for weights, and EBS-snapshotted compile cache (Spec C-EBS). A fused snapshot (Spec E) fuses env + weights + compiled state + process state into one binary and restores it on a fresh node — useful only when the stack is frozen, vLLM, and autoscale events are frequent enough that 25-40 s vs 50-120 s is load-bearing.

When to use
Spiky autoscale (>5 events/day), multi-tenant model-per-tenant fleets, capacity-resilient deployments, scale-to-zero with infrequent events.
When NOT to use
Single-replica always-on (the deployment IS the warm pool — you are double-paying). Steady-state autoscale <1 event/day cannot amortize the bake cost.
  • Spec C-EBS — 386 s on a brand-new B200, ~25 s attach overhead, ~$30/mo per volume (production pattern)
  • MX warm pool (regional) — N=2 cross-AZ floor for spot-reclaim recovery
  • Three-tier (A+B+C-EBS) — 16 artifacts for a 10-model × 3-vLLM × 2-hw fleet
  • Fused snapshot (E) — 25-40 s replica-N restore, 60 artifacts for the same fleet (full produce-path on any layer change)
  • Cudagraph trim + prefetch — combined ~50% of warm-path time, single CLI flag changes
Specs A · B · C-EBS · E · regional-mx-warm-pool. Default to three-tier; add snapshot only if vLLM + frozen stack + frequent autoscale.

Tier 4 — Capacity & routing

High Multi-replica + variance-sensitive

Pull-based / capacity-aware routing only matters when you have backends to route between AND the workload has request-cost variance OR prefix locality OR SLO tiers. Round-robin is correct for single-replica or fully-fungible-request workloads. Above that, GAIE EPP scorers (prefix, KV-utilization, SLO-headroom), Dynamo's global router, and custom heterogeneous-fleet scorers each address a specific pattern.

When to use
Multi-replica with shared prompts (Preble territory, 2-3× p99 TTFT win), SLO tiers (interactive vs batch), multi-region resilience, heterogeneous fleets.
When NOT to use
Single replica or fully fungible requests — routing is theatrical. AWS ALB does NOT implement Inference Extension; do not reach for it.
  • GAIE EPP v1.5.0 with prefix + kvcacheutilization — 2-3× p99 TTFT on prefix-heavy slices
  • SLO-tiered admission — prevents batch from blowing interactive p99
  • Dynamo global_router — <30 s automatic multi-region failover vs minutes manual
  • Heterogeneous-fleet scorer — open research; lab uniquely positioned to measure
  • Online-learned latency predictors — sparse literature, opportunity for measurement
global-inference-gateway-research · cold-start-autoscaler-policy · GAIE EPP InferencePool GA API.

Tier 5 — Frontier-model patterns

Very high Engineer-quarter-per-technique

Disagg P/D (DistServe / NIXL / Mooncake), request migration (Llumnix), multi-node TP, KV cache offload, and speculative decoding. Each has real wins on a narrow band of frontier-model workloads, and each costs an engineer-quarter to operate. The 80/20 cutoff is steep — most workloads should never reach for Tier 5. Half of these techniques have known traps: speculative decoding degrades on PCIe interconnects and produces degenerate "hello hello" output on synthetic random workloads.

When to use
Frontier MoE (>200B activations) on multi-node TP, RL/agent harnesses with extreme tail latency, KV-bound >32K-context workloads.
When NOT to use
Anything that fits TP≤8 on one node. Anything <200B activations. Short-context, short-response, or PCIe-interconnected GPUs.
  • Disagg P/D — only when single-node fit fails AND prefill/decode SLOs differ AND KV transfer beats re-prefill
  • Multi-node TP — GLM-5 744B, Kimi K2.6 1T, Qwen3-235B beyond TP=8 fit
  • KV cache offload (Mooncake-style) — long-context (>32K) where re-fetch latency < offload latency
  • Llumnix request migration — RL/agent harnesses with >10-min generations and severe tail
  • Spec decoding (MTP / draft-target) — single-replica large-model decode-dominated workloads on NVSwitch fabrics
dynamo-hyperpod · glm5-llmd · kimi-k2.6-speculative · glm5-lmcache. Gotchas tracked in MEMORY.md.
The single most-misadopted technique

Disagg P/D — the hard truth

Trap warning

Disagg prefill / decode is only really needed for frontier workloads.

Pretending you need it when you do not is the most expensive complexity tax in the lab. NIXL disables cuda_ipc by default to avoid NVSwitch contention, and TP=1 ends up as the sweet spot for the KV transport — the very pattern you do not get to use if you have multi-node TP. If your workload is "Ministral-3B / Qwen3-30B / Mistral-Small fits TP≤4 on one node," you do not need disagg.

Signs you actually need it

  • Model is too big for any single-node TP fit (GLM-5 744B, Kimi K2.6 1T, frontier MoE)
  • Prefill SLO and decode SLO are explicitly different (e.g., interactive prefill ≤200ms, streaming throughput dominant)
  • KV transfer over NIXL/RDMA is faster than re-prefilling — only true at very long contexts

Signs it is a trap

  • Anything that fits TP≤8 on a single node — multi-node NCCL overhead dominates
  • Mixing P/D at small scale costs latency you do not recover
  • You read a vendor blog with "5× routing improvement" baselined against chunked-prefill-OFF
Cost framing: an engineer-quarter to operate. Each of disagg P/D, request migration, multi-node TP, and KV offload imposes its own engineer-quarter. Stacking them naively imposes the union, not the intersection. Budget accordingly.
Architectural choice within Tier 3

Three-tier (A + B + C-EBS) vs fused snapshot (E)

The single biggest decision inside Tier 3. The 60-vs-16 artifact-count math is the headline: a fused snapshot grows multiplicatively across (model × vLLM × hardware), while three-tier separation grows additively.

Dimension Three-tier (A + B + C-EBS) Fused snapshot (E)
Artifact count 10 models × 3 vLLM × 2 hw 16 (10 weights + 6 env images) 60 snapshots
Invalidation surface Independent per layer Any layer triggers full rebake
Engine compatibility vLLM, SGLang, TensorRT-LLM vLLM only (preview)
Replica-N cold start (Ministral-class) 50-120 s 25-40 s
Operational complexity Low Medium-high
Best for Default for any production workload Spiky autoscale on frozen vLLM stack
Steering rule (codified in .claude/steering/tech-stack.md)

Default to three-tier. Add snapshot only when all three conditions hold: stack frozen ≥1 week, autoscale events frequent enough that 25-40 s vs 50-120 s is load-bearing, engine is vLLM. Everywhere else, three-tier separation is cheaper to operate and degrades gracefully under fleet churn.

Honest caveats

What this framework does NOT promise

Three honest caveats. Lifted directly from the source markdown — the framework is a decision aid, not a guarantee.

No specific number for your workload

workload pattern dominates
  • The ranges in this doc are typical, not guarantees
  • p50 / p99 split, prompt-length distribution, prefix locality each move the answer
  • Validate with your own measurement before committing engineering quarters

Higher tiers do not always help

they help only when the pattern justifies them
  • Tier 5 on small workloads costs more than it saves
  • Tier 4 prefix routing on fungible-request workloads is theatrical
  • Tier 3 snapshot on engines other than vLLM is unsupported

Tiers compose sub-linearly

stacked wins are not additive
  • Snapshot's 25-40 s floor sits on top of EBS+FSR's ~19 s overhead
  • The lab's measurements show clean composition but compounding wins are sub-linear
  • Treat stacked Pareto numbers as best-case single-replica, not aggregate fan-out
