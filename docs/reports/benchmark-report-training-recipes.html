Meta-Insights: Autoresearch Pattern

Conservative Exploration Under Context Limits

Sonnet 4.6 in --print mode explored only hyperparameters across 16 experiments — no architecture, multi-GPU, or torch.compile changes. Karpathy's Opus run discovered ~20 improvements across diverse categories in 118 experiments (12+ hours). The single-response context limit (--print) caps exploration depth. A wrapper script or interactive mode is needed for deeper runs.

86% MFU Headroom Is the Biggest Untapped Opportunity

At 13.9% MFU on a single GPU with 3 more GPUs idle, the model is dramatically compute-underutilized. Multi-GPU (DDP on 4 GPUs with Gloo backend), larger batch sizes, or torch.compile optimizations could 4-7x throughput — enabling 4-7x more training steps in the same 5-minute window. This is the likely path to the next major val_bpb improvement.

5-Minute Budget Favors Optimization Over Architecture

Deeper models (8→10 layers) regressed because they couldn't converge in 340 steps. All kept improvements were learning rate tuning — making the existing architecture train faster. Architecture exploration requires either a longer time budget or a model small enough to train more steps.

Blackwell Compatibility Tax

FA3 kernels lack sm_120 binaries. FA4 (CuTeDSL) requires bleeding-edge FlashAttention not yet in PyTorch 2.9.1. The flex_attention/SDPA workaround works but may leave performance on the table. On Hopper (sm_90), the repo runs unmodified.

Methodology

Autoresearch Loop

Each experiment follows a strict cycle: hypothesize → edit → run → measure → keep/revert. The agent proposes a single hyperparameter or architecture change, edits train.py, runs the training script for 5 minutes wall-clock, reads the final val_bpb from stdout, and either keeps the change (if val_bpb improved) or reverts to the last known-good version (if it regressed or was neutral). Changes accumulate — each kept improvement becomes the new baseline for subsequent experiments.

Fixed vs Editable Separation

prepare.py is frozen: it downloads FineWeb-Edu data, tokenizes with BPE (vocab 8,192), and defines the evaluate_bpb() metric. The agent can only modify train.py, which contains hyperparameters, model architecture, optimizer config, and the training loop. This separation ensures the evaluation metric cannot be gamed.

Evaluation Protocol

The metric is val_bpb (validation bits-per-byte) — lower is better. It is computed by prepare.py's evaluate_bpb() over a held-out validation shard after each 5-minute training run. The 300-second wall-clock budget includes torch.compile JIT warmup (~26s), so effective training time is ~274s (~340 optimization steps at the baseline batch size).

Blackwell Compatibility Fix

FlashAttention 3 kernels (kernels-community/flash-attn3) lack sm_120 binaries for Blackwell. FlashAttention 4 (CuTeDSL backend) requires a bleeding-edge checkout not yet in PyTorch 2.9.1. Fix: Replace the FA3 import with a _FA3Compat wrapper using torch.nn.attention.flex_attention (compiled Triton kernels with create_block_mask for sliding window) and F.scaled_dot_product_attention (SDPA) for full causal attention. Layout conversion handles FA3's (B,T,H,D) vs flex/SDPA's (B,H,T,D).

Agent Setup

Claude Sonnet 4.6 via Amazon Bedrock, invoked through Claude Code CLI in --print mode (single response, no interactive follow-ups). The agent receives the codebase context, baseline metrics, and instructions in a single prompt, then outputs all experiments sequentially. This caps exploration depth to what fits in one response (~16 experiments). A wrapper script or interactive mode would be needed for longer runs (100+ experiments).
