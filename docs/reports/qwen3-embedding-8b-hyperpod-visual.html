Key lessons (from lessons.md)

Performance is compute-bound, not memory-bound

Throughput scales near-linearly with concurrency to c=32 across all workloads (0 OOM, 0 errors). The A10G is working hard on every request, not blocked on KV/memory pressure.

Context length drives the ceiling more than concurrency

Going from 1K → 8K tokens drops throughput ~30% at c=16. Applications with long documents must plan ingest throughput against the long-tail of the context distribution, not the median.

T5 is disproportionately large for embeddings

T5 kernel tier is the "last 15%" for generative LLMs. For compute-dense, single-pass workloads like embeddings, T5 is the entire story: 21.3× at c=32, no other tier applicable.

T0 saturates around 6 req/s regardless of concurrency

Classic "compute-starved by scheduling overhead" shape — T0 eager mode can't batch past ~6 req/s because every request triggers a full Python interpreter loop without CUDA graph capture. T5 scales near-linearly up to c=32.

Burn-in drift gate must be directional, not bidirectional

Original rule was "±2% drift" — this failed legitimately-passing runs where throughput improved by >2% (post-warmup stabilization). Fixed to "degradation ≤ 2% OR improvement ≤ 5%". Applied to standards/benchmark-commons/workloads/burn-in.yaml and container/analyze-burn-in.py.

22× cheaper than OpenAI text-embedding-3-large

At ~600 tokens per embedding, OpenAI API = ~$78/M embeddings. Self-hosted on ml.g5.4xlarge spot = $3.44/M embeddings. The per-embedding cost delta exactly tracks the T5/T0 throughput ratio.
