▼ Stock OSS vs CoreWeave (added 2026-05-15)

vLLM+NVFP4 ≈ SGLang+FP8+EAGLE3 ≈ 63 tok/s on real ShareGPT — both ~2× behind CoreWeave

Direct head-to-head on the same Kimi K2.6 weights, ShareGPT replay (200 real conversations, c=16):

SGLang TP8 + FP8 + EAGLE3 + HiCache: 63.8 tok/s/req · accept rate 0.347 · accept length 2.39
vLLM TP4 + NVFP4 (no spec decode): 63.3 tok/s/req · no spec
CoreWeave (NVFP4 + custom kernels): 128.2 tok/s per Artificial Analysis
Provider median (11 providers): 52.9 tok/s

NVFP4 alone doesn't close the gap. Switching from FP8+EAGLE3 to NVFP4+nospec on stock vLLM is a wash on real workloads — the half-bandwidth savings are eaten by losing EAGLE3 (and by stock NVFP4 kernels not fully exploiting FP4 tensor cores). CoreWeave's 2× lead is structural:

  • Custom NVFP4 cutlass 3.x kernels for B200/B300 FP4 tensor cores
  • Likely a custom-trained draft model on production traffic (accept rate ~0.7 vs our 0.35)
  • Possibly Kimi-specific MoE batching tuning

Synthetic-vs-real gap: our Phase 1 single-stream c=1 numbers (164 / 302 tok/s) were on uniform "hello..." prompts where the EAGLE3 draft accepts every token (rate 1.0). On real ShareGPT conversations the accept rate drops to 0.347 — barely better than no spec decode. The synthetic ceiling overstates real production gains by 3-5×.

▼ Engine choice · the clean narrative

vLLM wins throughput · SGLang+EAGLE3 wins per-token latency

The two engines optimize for different workloads and the consolidated data makes the split obvious:

Throughput @ c=512: vLLM 10,437 tok/s vs SGLang 3,400 tok/s → vLLM wins 3.1×
Per-request @ c=1: SGLang+EAGLE3 302 tok/s vs vLLM baseline 76 tok/s → SGLang wins 4.0×
Warm-batch TTFT @ c=8: vLLM 54 ms vs SGLang 388 ms → vLLM wins 7× (batched)
Cold TTFT @ c=1: SGLang 4,646 ms vs vLLM 11,937 ms → SGLang wins (both bad)

Rule of thumb for customer conversations:

  • High-QPS API serving (chat completions, bulk generation, batch jobs) → vLLM TP8 + prefix caching. Max aggregate throughput, best warm TTFT, cheapest $/M tokens.
  • Interactive agent / coding assistant (each user perceives per-token decode speed) → SGLang TP8 + EAGLE3 s4_d4_k1 + HiCache. 302 tok/s per request feels 4× faster than vLLM baseline on the user's screen.
  • Mixed multi-tenant (c=32–256 sustained, moderate latency sensitivity) → SGLang TP4+DP2 + EAGLE3 + HiCache. Beats vLLM baseline on both aggregate (+28% at c=256) and per-request.
⚠ Phase 1 methodology error overturned (L17)

EAGLE3 defaults hide the real picture — tuned config is a major win

The prior session concluded "EAGLE3 hurts aggregate throughput" based on SGLang defaults (num_steps=3, num_draft_tokens=4, topk=1). The sweep proves the conclusion was wrong — with num_steps=4, EAGLE3 produces 302 tok/s single-stream (+136%) and 6,410 tok/s @ c=128 (+75% over Phase 1). K2.6's EAGLE3 draft accepts all 4 tokens per step — draft model is stronger than the defaults assume.

▼ L19 · CUDA graphs are the dominant optimization

CUDA graphs deliver 6.4× speedup on Blackwell spec decode

Phase 5b isolates cuda graphs by running with --disable-cuda-graph while keeping everything else identical:

c=1 per-req: 298 → 47 tok/s (−84% without graphs = 6.4× speedup from graphs)
c=128 agg: 6,143 → 1,906 tok/s (−69% = 3.2× speedup)
c=256 agg: 7,173 → 2,032 tok/s (−72% = 3.5× speedup)

Without graphs, EAGLE3's draft+verify Python/launch overhead dominates entirely. This is the single most important lever in the Blackwell + spec decode stack.

▼ L18 · SGLang engine quirk

--speculative-num-draft-tokens is a no-op in this range

Within a fixed num_steps, sweeping num_draft_tokens ∈ {2, 4, 6, 8} produces identical results and accept_length = num_steps+1 everywhere. SGLang only expands the draft tree to num_steps depth. Future sweeps should fix num_draft_tokens = num_steps and only vary num_steps and eagle_topk.

The next ceiling — production optimization beyond engine tuning

The measurements above represent the best a single-tenant, statically-configured inference engine can do on this hardware. Moving from 16% of BW roofline (today) to ~30–35% (realistic ceiling) requires a different category of work — production-workload optimization, not kernel optimization. These problems don't show up in a benchmark but dominate real-world cost.

Cross-request KV fragmentation At c=512, KV cache churn and page fragmentation wastes 10–15% of HBM BW. vLLM PagedAttention captures some of this; SGLang radix cache captures less. Deeper fix requires invasive engine changes. +30–50% at bulk load Engine-internal · hard to upstream cleanly
Multi-tenant request routing OSS engines are single-process. Real workloads need priority queues, fair-share across tenants, rate limits, SLO-aware admission control. The engine running flat-out is 40% of the cost story — the other 60% is how you dispatch. +40–80% effective capacity Above the engine · product-layer code
Fleet-level autoscaling on GPUs Cold-start is 4–16 min per replica. Naive HPA keeps too many warm replicas (cost) or scales too slow (latency). ▼ Strategic framing

Engine tuning has a ceiling. Production-workload optimization does not (yet).

Today's best single-node measured throughput is 10,437 tok/s (bulk) / 302 tok/s per-request (agentic). The realistic single-node ceiling in 12–18 months — assuming upstream OSS captures most of the software gap — is ~18–20K tok/s bulk / ~400 tok/s agentic on this same hardware. That's maybe 2× from engine-side work alone.

Beyond that, cost improvements come from the rows above: request routing, multi-tenant fleet autoscaling, compound serving, and traffic-tuned model ops. These are where the next 3–5× of effective $/M-tokens savings live at enterprise scale.

The critical economic crossover: at <$200K/yr inference spend, OSS self-hosted + a good engine config wins. At $200K–$2M, the operational levers above pay back faster than staffing to build them in-house. At >$2M/yr with latency-sensitive product requirements, building above the engine (routing, LoRA, autoscaler, compound) while keeping the engine pristine and upstream-tracking is the durable path — forking the engine itself is a maintenance tax that almost never pays back.
