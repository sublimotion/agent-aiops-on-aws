▼ The synthetic-vs-production gap (L15) — must read

Synthetic prompts overstate EAGLE3 throughput by 3-6×

Every "Phase 1b winner 325 tok/s" number in this report is from synthetic uniform "hello hello..." prompts where the EAGLE3 draft trivially predicts every token (accept rate 1.0, accept length 5.0). On real ShareGPT conversation traffic at the same config:

Per-request decode @ c=1 (synthetic): 325 tok/s
Per-request decode on ShareGPT (real, c=16): 54 tok/s
Accept rate on real traffic: 0.156 (15.6%, vs 100% synthetic)
Accept length on real traffic: 1.62 (vs 5.0 synthetic)

This means production routing recommendations based on synthetic numbers overstate EAGLE3's value 3-6×. All synthetic numbers in this report are useful for engine-vs-engine comparison at fixed prompt distribution, but they do NOT predict production throughput. When quoting numbers to customers, always lead with the ShareGPT number.

▼ Stock OSS ceiling vs commercial providers (L16, L18)

vLLM+NVFP4 ≈ SGLang+FP8+EAGLE3 ≈ 63 tok/s on real ShareGPT — both ~2× behind CoreWeave

Tested directly on the same node: vLLM TP4 + NVFP4 (no spec) = 63.3 tok/s vs SGLang TP8 + FP8 + EAGLE3 + HiCache = 63.8 tok/s on ShareGPT (c=16, 200 conversations). NVFP4's halved HBM bandwidth advantage and EAGLE3's speculative-decode advantage roughly cancel out — neither alone closes the gap to CoreWeave's 128.2 tok/s (Artificial Analysis).

This kills the "just enable FP4" narrative. CoreWeave's 2× lead comes from:

  • Custom NVFP4 cutlass 3.x kernels exploiting B200/B300 FP4 tensor cores (vLLM v0.19's compressed-tensors path is more generic, not as tuned)
  • Likely a custom-trained draft model on production conversation traffic (would boost accept rate from 0.35 → 0.7+)
  • Possibly Kimi-specific batching tuned for the 384-expert MoE architecture

Customer-facing rule: Stock OSS on B300 in mid-2026 caps at ~60-65 tok/s decode on Kimi K2.6 ShareGPT, regardless of engine choice. Closing the gap to commercial providers requires real engineering investment (kernels + drafts), not just config tuning. If a customer doesn't need that last 2× and just wants OSS + reproducibility, our stack is competitive with the median provider (52.9 tok/s) and ~50% of the top-tier providers.

▼ Engine choice · the clean narrative

vLLM wins bulk throughput · SGLang+EAGLE3 wins per-token latency

Same story as Kimi K2.6-speculative. Qwen3-235B's EAGLE3 draft accepts 5 tokens/step (better than its own model card claims) and crushes single-stream; but at extreme c=512 the vLLM TP2+DP4+EP baseline still edges out on raw aggregate.

Single-stream c=1: SGLang+EAGLE3 325 tok/s vs vLLM baseline 103 → +216%
Multi-tenant c=256: TP2+DP2 15,336 vs vLLM TP4 8,058 → +90%
Multi-tenant c=256 (vs DP4+EP): 15,336 vs vLLM TP2DP4EP 9,019 → +70%
Bulk c=512: SGLang Phase 4 9,739 vs vLLM TP2DP4EP 13,877 → −30% (vLLM wins)

Routing rules for production Qwen3-235B:

  • Agentic / single-user (c ≤ 16) → SGLang TP4 + EAGLE3 s4d4k1 + HiCache. 322 tok/s per request feels 3× faster than vLLM baseline.
  • Multi-tenant moderate (c = 32–256) → SGLang TP2+DP2 + EAGLE3 + HiCache. Beats every other config at both aggregate AND per-request.
  • Bulk throughput (c ≥ 512) → vLLM TP2+DP4+EP + prefix caching, no spec decode. 13,877 tok/s at $0.33/M.
⚠ L18 cross-model generalization

num_draft_tokens is a no-op in SGLang — confirmed on second model

Within fixed num_steps, sweeping num_draft_tokens ∈ {2, 4, 6, 8} produced nearly-identical results on both Kimi K2.6 (MLA) and Qwen3-235B (GQA). Accept length always equals num_steps + 1 regardless of draft budget. SGLang only expands the draft tree to num_steps depth. This is an engine-wide pattern, not a model-specific one. Future EAGLE3 sweeps should fix num_draft_tokens = num_steps + 1 and only vary num_steps and eagle_topk.

▼ Cross-architecture surprise · GQA vs MLA

CUDA graphs are only 17% on Qwen3-235B (vs 6.4× on Kimi K2.6)

Phase 5b isolates cuda graphs by running with --disable-cuda-graph. On Kimi K2.6's MLA architecture, disabling graphs collapsed c=1 per-req from 298 to 47 tok/s (6.4× speedup from graphs). On Qwen3-235B's GQA architecture the same ablation barely moves the needle:

Qwen3-235B c=256 agg: 9,608 → 8,207 (−15%, 1.17× speedup from graphs)
Kimi K2.6 c=256 agg: 7,173 → 2,032 (−72%, 3.5× speedup from graphs)

Interpretation: GQA's simpler attention pattern has fewer small kernel launches.
MLA's compressed-KV expansion generates many more CUDA launches that graphs eliminate.

Implication: if a future vLLM-only env can't enable CUDA graphs with EAGLE3, the penalty on Qwen3-class GQA MoE models is tolerable (~15%), but the same flag would be catastrophic on MLA models. Architecture matters more than engine choice here.
