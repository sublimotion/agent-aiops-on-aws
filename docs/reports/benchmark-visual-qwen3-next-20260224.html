4K–64K: Viable under SLOs

TTFT scales roughly linearly. Output throughput stable at 123–125 tok/s. ITL p99 stays under 10 ms. DeltaNet linear attention helps keep the slope manageable.

TTFT p50 = 5.8s (7.7x worse than 64K). ITL p99 = 604 ms (20x over 30ms SLO). The O(n²) standard attention layers dominate at this context length. Practical limit: 64K.

DP+EP: Not Recommended

TP=4 is strictly superior — higher throughput with half the GPUs, and meets all SLOs. DP+EP's expert parallelism adds cross-GPU MoE routing overhead (512 experts, 10 active per token) that dominates at single-node scale. The 4 idle GPUs from TP=4 are better used for a second replica.

Blocked Configurations

Configurations that could not be benchmarked due to software limitations

TP=8 — FP8 block_k Incompatibility (Both Engines)

FP8 quantization uses block_k=128. With TP=8, the shared expert MLP down_proj partitions to input_size=64, not divisible by 128. Affects both vLLM and SGLang. Would require BF16 (2x memory) to use TP=8.

MTP Speculative Decoding — vLLM 0.16 V1 Bug

V1 engine _dummy_run warmup doesn't account for speculative tokens: AssertionError: num_tokens <= max_num_batched_tokens. Tested with num_speculative_tokens=1,2 and batch sizes 32K/64K. All fail. Requires vLLM 0.17+.

T5d: KV Cache Offloading — BLOCKED (6 Approaches)

All KV cache offloading approaches blocked for Qwen3-Next due to hybrid attention architecture requiring HMA

# Approach Target Tier Blocker Status
1 --cpu-offload-gb GPU → CPU (weights) V1 engine AssertionError (asserts cpu_offload_gb == 0) BLOCKED
2 Dynamo KVBM GPU → CPU → Disk dynamo-run CLI removed in ai-dynamo 0.9.0 BLOCKED
3 OffloadingConnector GPU → CPU (KV) HMA disabled by kv-transfer-config → can't unify KV specs BLOCKED
4 LMCacheMPConnector GPU → CPU (KV) Same HMA error — no connectors implement SupportsHMA BLOCKED
5 LMCache + FSx GPU → CPU → FSx Lustre HMA catch-22: enabled → connector rejects; disabled → specs fail BLOCKED
6 Dynamo + TRT-LLM Alt engine + KV tier Qwen3NextForCausalLM not in TRT-LLM (any version) BLOCKED

Root Cause: HMA + Hybrid Attention Catch-22

Qwen3-Next interleaves full attention (every 4th layer) with linear attention, creating different KV cache specs per layer group. This requires vLLM's Hybrid KV cache Manager (HMA). But all KV connectors (OffloadingConnector, LMCacheConnectorV1, LMCacheMPConnector) auto-disable HMA via KVTransferConfig. With HMA disabled, vLLM can't unify the specs → ValueError. With HMA enabled, connectors reject because none implement SupportsHMA.

TRT-LLM: Architecture Not Supported

model_type: qwen3_next requires transformers 4.57.0.dev0 (unreleased). TRT-LLM 0.17.0 has Qwen2MoeForCausalLM; TRT-LLM 1.1.0 (latest) added Qwen3MoeForCausalLM but not Qwen3NextForCausalLM. Architecture is distinct — hybrid attention, linear heads, shared experts, partial_rotary_factor=0.25. Can't be remapped to Qwen3MoE.

GDS (GPUDirect Storage): Not Available

nvidia_fs kernel module not installed on instance. libcufile not present. Would be irrelevant anyway — LMCache uses CPU DRAM as intermediary, not direct GPU→storage DMA. GDS would only help if a connector supported direct GPU→FSx writes, which none do.

Impact Assessment: Offloading Unnecessary on H200

H200 provides 104.5 GiB KV cache per GPU at 0.92 utilization, enough for 34.6x concurrency at 262K context. KV offloading would only matter at extreme concurrency (>30 simultaneous 262K requests per replica). For typical workloads (QPS 4–8, mixed context lengths), GPU VRAM is not the bottleneck — prefill computation is.

Prefix Cache Extends Viable Context to 252K

With a 200K shared prefix + 128 suffix, TTFT p50 drops from 2.2s to 860 ms (2.6x improvement). ITL p99 drops from 576ms to 20 ms (28.8x improvement) — comfortably within the 30ms SLO. This enables RAG patterns with shared document context at full native context length.

Batching Transforms 126K Viability

At QPS 2.0, TTFT p50 drops from 1,201ms to 261 ms (4.6x) and ITL p99 from 422ms to 57.7 ms (7.3x). Long-context workloads should target moderate concurrency (QPS 2.0+) where GPU batching amortizes the O(n²) prefill cost.

CPU Offload: Blocked & Unnecessary

--cpu-offload-gb is incompatible with vLLM 0.16 V1 engine (AssertionError in may_reinitialize_input_batch). VLLM_USE_V1=0 not recognized (V0 removed). Irrelevant on H200: 104.5 GiB available KV cache per GPU provides 34.6x concurrency at 262K without offloading.

64K/128K TTFT Targets Need Revision

The spec assumed DeltaNet linear attention would flatten TTFT scaling. In practice, the hybrid architecture interleaves standard O(n²) attention every 4th layer, and these layers dominate at long context. The TTFT targets at 64K (<500ms) and 128K (<1s) were overly optimistic.

Recommendations

Production deployment guidance based on benchmark findings

Production Config

vLLM TP=4 at QPS 4–8 on 4 GPUs. --enable-prefix-caching always on. Two replicas on the same instance for ~2x aggregate throughput.

Context Limit

Use --max-model-len 262144. 64K for random workloads at low QPS. 126K viable at QPS 2.0+ (batching). 252K viable with prefix caching (shared document/system prompt pattern).

Prefix Caching

Structure workloads to maximize prefix reuse: shared system prompts, code context. 58% TTFT reduction at 30K prefix. Extends viable context to 252K (ITL p99 = 20 ms within SLO).

Avoid DP+EP

Expert parallelism overhead dominates. TP=4 achieves higher throughput with half the GPUs and meets all SLOs.

MTP: Revisit Later

Wait for vLLM 0.17+ to fix the V1 warmup bug. MTP could significantly improve ITL (decode latency).

Cost

~$3.78/1M output tokens with 2× TP=4 replicas (capacity block $41.61/hr, QPS 4 each). On-demand ($98.32/hr): ~$8.94/1M. Single replica doubles these figures.

KV Offloading: All 6 Approaches Blocked

All KV offloading paths (cpu-offload, Dynamo KVBM, OffloadingConnector, LMCacheMPConnector, LMCache+FSx, Dynamo+TRT-LLM) are blocked due to the HMA/hybrid-attention catch-22. Unnecessary on H200 — 104.5 GiB KV cache per GPU provides 34.6x concurrency at 262K. Requires vLLM connectors to implement SupportsHMA or TRT-LLM to add qwen3_next support.
