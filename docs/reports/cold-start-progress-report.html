Why the 17.2% number is load-bearing

Modal's 2026 writeup conjectured "~1,000 of N files actually read" for typical Python imports. Our measurement nails this for vLLM: 17.2% of bytes, 9.5% of files. That's the theoretical ceiling for any lazy-pull mechanism — SOCI, Nydus, OCI Image Volume — on a vLLM image. A perfectly-tuned eager pull still moves 5.8× more bytes than necessary. EBS prebake remains useful (one-time cost amortized across replicas), but for autoscale lazy wins.

Headline finding — the EBS-snapshot pattern works

Bake compile cache to a fresh EBS volume. Snapshot it. Tear down the GPU. Bring up a brand-new B200 in the same AZ. Create volume from snapshot in 8.84 s. Attach in 9.7 s. Mount in <1 s. AOT cache HIT confirmed in logs for all 8 TP ranks. Cache survives node termination, AZ-locked but cheap (~$30/mo for 700 GB), and supports multi-variant coexistence (vLLM auto-keys by config hash). This is the production-ready pattern for delivering Modal-style AOT compile cache speedup on EKS without proprietary infrastructure.

The remaining bottleneck — weight load (245 s) — is post-page-cache

With prefetch ON (8 threads × 16 MB), page cache fills in 8.66 s for 585 GB on instance NVMe (~67 GB/s). But the main loader still spends 245 s on cudaMemcpy + per-tensor torch overhead. That's the new floor. Two paths below it: ModelExpress same-node P2P (replica-N≥2 via NVSwitch at 250 GB/s, deferred experiment), or vLLM internals work (batched H2D copies, pinned memory, stream overlap — out of scope for this lab).

What we learned

Five Concrete Findings

1. Warm cache wins 5.4×

Kimi K2.6 FP8 cold-S3 → warm-NVMe
46 min → 8:30
  • S3 sync of 585 GB takes 32 min on B300 (~17 GB/min steady).
  • Once cached on instance NVMe, that disappears. The .staged marker in init container is enough.
  • This is just "Smart Cache DaemonSet" applied correctly — no new infra needed.
  • Implication: warm node pool with image-prepull-style weight prepull is high-leverage.

2. JIT dominates warm path

Even tiny Qwen3-1.7B spends 70 of 102 s on compile
~70%
  • For a 1.7B model on B300 (the easy case), JIT + CUDA graph capture is 70 % of cold start.
  • For Kimi K2.6 on warm path, JIT + capture is ~75 % of remaining 8:30.
  • This is the stage Spec C targets.
  • Without compile-cache work, every replica pays this cost from scratch.

3. Modal sets the achievable floor

AOT compile cache HIT on H200, 26B MoE
~22 s
  • Backbone Dynamo + AOT load: 13.96 s.
  • Drafter Dynamo + AOT load: 2.82 s.
  • Profiling/warmup: 5.34 s.
  • Cache files in /root/.cache/vllm/torch_compile_cache/... — portable, format binary.
  • This is what Spec C will reproduce on EKS+PVC.

4. CUDA graph capture is NOT cached

Modal default = 51 sizes, ≥100 s capture
≥100 s
  • Even with AOT cache HIT, 51 cudagraph sizes (1, 2, 4, ..., 512) take 100+ s to capture.
  • Capture is keyed on dynamic shapes seen at runtime.
  • Trimming to ~10 production batch sizes reclaims 60-80 % of this stage independent of cache.
  • Two independent levers: cache (Spec C) + capture-set tuning (separate).

5. flashinfer JIT is a known papercut

Crashes both Modal app and our slim image at the same code path
  • vLLM v1 sampler calls flashinfer.sampling.top_k_top_p_sampling_from_logits.
  • flashinfer JITs the kernel with ninja the first time it's hit.
  • Slim runtime images without nvcc crash. Modal hits the same KeyboardInterrupt during build.
  • Workaround: dummy completion request during cache-baker CI to populate flashinfer cache, then bake or PVC-mount.

6. Spec 0 profiler works

Canonical 14-event timeline captured cleanly across 6 runs
  • 5 Qwen3-1.7B + 2 Kimi K2.6 measurements all produced complete stage attributions.
  • Stage durations sum to ≥95 % of total (validation criterion met).
  • Run-to-run σ/μ on Qwen3 stages all under 0.5 (variance criterion met).
  • Profiler is ready for Specs A/B/C/D to consume.

New Findings (2026-05-31)

Spec E · Dynamo Snapshot (CRIU process C/R)

NVIDIA Dynamo Snapshot uses cuda-checkpoint + CRIU to serialize an entire warmed-up vLLM worker process to disk and restore it on a fresh node. This is a different primitive from Spec C-EBS: where C-EBS snapshots the AOT compile-cache directory on a block volume, Spec E snapshots the process tree including GPU device state, fds, and pinned host memory. The two compose — a fresh node can mount the EBS compile cache and restore from a Dynamo snapshot — but they attack different stages.

Single-GPU primitive · PASS

g6.xlarge L4 (sm_89), Qwen3-0.6B FP16, CRIU 4.2 + PR #3021
  • Gate 1 (token-ID equality): PASS — SHA256 byte-identical across restore.
  • Gate 3 (restore wall-clock): 1.69 s for 4.14 GiB artifact (~1.95 GiB/s).
  • Gate 2 (artifact ratio): 2.93x on 0.6B is dominated by ~3 GiB fixed Python/torch/CUDA overhead.
  • Extrapolation: Ministral-3B = 1.50x, Mistral-Small-4 = 1.25x, Gemma-4-26B = 1.12x — all PASS.
  • Predicted cold-start: 15-45 s vs 100-240 s baseline = 5-10x on Ministral-class.

Multi-GPU bare-metal · BLOCKED

p5e.48xlarge (8× H200), CRIU dump fails on bare /dev/nvidiaN fds
  • NVIDIA driver opens 51 fds across all 8 /dev/nvidiaN regardless of CUDA_VISIBLE_DEVICES — used for NVLink/NVSwitch topology discovery.
  • cuda_plugin only registers HANDLE_DEVICE_VMA; bare-fd opens fall through to dump_unsupp_fd → -ENOTSUP.
  • NVIDIA's K8s snapshot-agent sidesteps this via nvidia-container-runtime OCI hooks that hide peer GPU device nodes.
  • Pivot: containerized execution with --gpus '"device=0"' is the next experiment.
  • Gemma-4 anchor cell vs Modal's 22 s AOT-HIT floor is deferred until container path validated.
Read carefully — Spec C-EBS vs Spec E are NOT the same thing

Spec C-EBS (compile-cache snapshot, production-ready): bake vLLM's torch_compile_cache/ onto an EBS volume, take an EBS snapshot, mount on each fresh node via the EBS CSI driver. Eliminates the JIT/compile + CUDA-graph capture stages. AOT cache HIT in ~25 s overhead. Block-storage operation.

Spec E (Dynamo Snapshot, single-GPU PASS / multi-GPU bare-metal BLOCKED): cuda-checkpoint serializes GPU device state, then CRIU dumps the full process tree (memory + fds + CUDA contexts). Restore brings back a fully warmed-up vLLM worker. Eliminates model load + JIT + first-token warmup in a single step. Process-level C/R, requires kernel CAP_CHECKPOINT_RESTORE + driver 580.xx+.

Spec C-EBS is the production default for any model size, any TP. Spec E is the single-GPU replica-N≥2 fast-path: when an autoscale signal arrives and a warmed worker artifact already exists for the exact (model, engine version, driver, hardware) tuple, you skip not just compile but also weight load.

Operational gotchas captured during Stage 0

(1) CRIU PRs #3021 + #3022 conflict on criu/mem.c; merging both requires hand-resolution. Bridging cell took #3021 (parallel-memfd) only. (2) io_uring is unsupported in CRIU even with NVIDIA's PRs; vLLM's uvloop dep triggers it. NVIDIA's snapshot-agent injects a seccomp profile blocking io_uring_* syscalls so libuv falls back to epoll. (3) Host RAM ≥ 1.2× peak GPU alloc + 4 GiB — cuda-checkpoint copies device state to host before CRIU dumps. A g6.xlarge at gpu_memory_utilization=0.85 OOMs on the L4's 19.7 GiB GPU footprint. (4) Use sleep(level=1) only — level=2 unloads weights and breaks token-ID equality on restore (different CUDA context post-wake_up). (5) AMI-bake pattern survived two spot reclaims cleanly (~$0.05 add cost, saves ~25 min rebuild per reclaim). Full recap: dynamo-snapshot-recap.html.

Two important caveats before quoting this number

(1) Concurrent-restore contention is unmeasured. When 4 replicas restore from one canonical snapshot simultaneously, EBS+FSR per-AZ throughput becomes the question. Cell E1 of dynamo-snapshot-eks-multinode exists specifically to measure this. Until that runs, treat ~25-40 s as best-case single-replica wall time, not aggregate fan-out.

(2) For larger models the curve gets better, not worse. The ~19 s EBS volume-create + attach overhead is fixed. Baseline scales with weights × bandwidth + JIT, so a GLM-5-class baseline (16 min) against a stacked floor still bottlenecked by ~20 s of EBS overhead is a much larger speedup multiplier than what Ministral-3B shows here.

Speedup multiplier framing

2-4× vs baseline for Ministral-3B class — not the 5-10× the standalone Spec E budget table promised, because EBS+FSR adds back ~20 s the pure-snapshot path doesn't pay if you cheat with FSx Lustre always-on. That's the actual cost of using EBS as the snapshot transport instead of paying $1,095+/mo for FSx P-1000.

Order of operations for the autoscaler: warm pool hit → image pull starts ‖ EBS volume-create starts → container start ‖ EBS attach → CRIU restore → first token. The two parallel-able pairs are what gets the floor below 30 s. Without overlap engineering in the autoscaler controller, expect the serial 25-64 s number instead.

Architecture · separation of env vs model vs compile-state

Three-tier persistence ladder vs the snapshot's fused artifact

Spec E fuses env + model + compiled state + process state into one binary blob. Specs A + B + C-EBS keep them separate, so each layer invalidates independently. Different operating cost profiles for different fleet shapes.

When fused wins vs when separated wins

Snapshot (Spec E) wins on: fast-twitch autoscaling on a stable stack — no recent vLLM bumps, weights stable, config locked. Replica-N≥2 events firing often enough that 25-40 s vs 50-120 s is load-bearing. vLLM-only.

Three-tier (A+B+C-EBS) wins on: environments where vLLM ships weekly, model fleet is multi-tenant, compile cache reuse is high, or the engine is SGLang (where snapshot is unsupported). Each layer invalidates without invalidating the others — a vLLM bump rebuilds image+compile-cache but reuses the entire weights cache; a weights swap reuses image+compile-cache.

Multi-tenant arithmetic: 10 models × 3 vLLM versions × 2 hardware tiers = 60 snapshots vs 10 weights + 6 env images = 16 artifacts for the three-tier path.

Production rule (also in .claude/steering/tech-stack.md)

Default stack: slim image (A) + EBS-snapshotted compile cache (C-EBS) + MX/RunAI weights (B). Add Dynamo Snapshot (E) only on the specific replica-pools where (a) the stack is frozen for ≥1 week between bumps, (b) autoscale events fire often enough that 25-40 s vs 50-120 s is load-bearing, and (c) the engine is vLLM. Everywhere else, the three-tier separation is cheaper to operate and degrades gracefully under fleet churn. Snapshot's compile-cache contribution can also be reproduced by C-EBS at a fraction of the bake cost — the unique value snapshot adds is the process state (CUDA graphs, pinned memory, NCCL state when in scope), not the compiled artifacts.

What was answered

  • Cudagraph trim is the cheapest big win — saves 162 s for one CLI flag (~$0.05/s saved)
  • Prefetch ON beats prefetch OFF on local NVMe — defeats vLLM's auto-disable heuristic, saves 141 s
  • Aggressive prefetch tuning is marginal — 32 threads × 64 MB beats 8 × 16 MB by only 10 s
  • RunAI Streamer is conditional — 0 s win on local NVMe (PCIe-bound), only useful for S3-backed sources
  • EBS-snapshot AOT cache works — same speedup on fresh node as same-node hostPath, 25 s overhead
  • Weight-load floor is post-page-cache — 245 s of cudaMemcpy work that no current technique addresses on TP=8

What's still open

  • ModelExpress same-node multi-pod — only path below 245 s weight-load floor; needs 2 pods on same B200; ~$60 to test
  • Spec A SOCI / Nydus — 17.2% access ratio is established; mechanism implementation deferred (low priority for our workload)
  • Spec E FUSE tuning — only relevant if Spec A SOCI runs
  • Variance tightening — most measurements are single-shot; 3 more replicates per cell would add error bars
Production-ready steering rules from this lab

1. Always set --compilation-config={"cudagraph_capture_sizes":[1,2,4,8,16,32,64,128,256,512]} (or your production batch sizes). Saves ~25-30%.
2. Always set --safetensors-load-strategy=prefetch on local NVMe. Saves ~25%. vLLM's auto-detection auto-disables this; force it on.
3. Bake AOT compile cache to EBS snapshot per (model, vLLM version, config hash). Mount as PVC. Cache HIT on every fresh node, ~25 s overhead, ~$30/mo storage.
4. Use slim image for any new vLLM deployment. 1.87× pull speedup just from shrinking, no infrastructure work.
5. Skip RunAI Streamer when source is local NVMe. Use only when source is S3 / network-attached storage.
6. Co-locate weight bucket with serving cluster. Cross-region S3 sync was 2× slower than in-region.
