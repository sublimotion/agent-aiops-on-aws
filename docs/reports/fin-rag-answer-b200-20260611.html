All 4 replicas live on ONE instance — the headline numbers are already the node aggregate

p6-b200.48xlarge = 8× B200. Each replica is TP=2, so the winning layout packs 4 replicas × 2 GPUs = all 8 GPUs on a single instance ($32/hr spot). The benchmark drove a ClusterIP that load-balanced 130 concurrent across all 4 replicas (~32/replica).

Read the table correctly: the 221,168 tok/s and $0.040 / 1M total tokens figures are the 4-replica node-level aggregate, not a single replica — do not multiply them by 4. The 4× is already included.

Dense packing is the cost-efficiency lever: a single TP2 replica alone would strand 6 of 8 GPUs, deliver ~¼ the throughput, and still cost the full $32/hr → ~$0.16/1M total (4× worse). Packing 4 replicas onto the node is what makes it 4× more cost-effective than under-packing it.

Optimization-grid legs

Leg 1 — FP8 KV cache on vs off → NO-OP

Dropping --kv-cache-dtype fp8 does not disable fp8 KV: vLLM 0.18.1 auto-selects kv_cache_dtype=fp8_e4m3 for the ModelOpt FP8 checkpoint (ships k/v scales). KV memory unchanged at 95.02 GiB. The 4,598 vs 4,685 delta is run-to-run noise on the identical fp8 path. KV footprint is not a lever here (507× concurrency headroom either way).

Leg 2 — FlashInfer vs TRITON_ATTN → FlashInfer faster, accuracy caveat smoke before adopt

FlashInfer loaded on this hybrid Mamba-2 model (contrary to spec caution) and is ~10% faster on E2E p50 (4,197 vs 4,685), ~18% lower TPOT (44.9 vs 55.0), 0 errors. Caveat: with fp8 KV, fp8 attention runs with uncalibrated q_scale/prob_scale = 1.0 (FP8 checkpoint lacks q/prob scales) — vLLM warns of possible accuracy impact (present on TRITON too, not unique to FlashInfer). Adopt only if a coherence smoke confirms no quality regression; otherwise keep TRITON_ATTN (hybrid-safe default).

Leg 3 — agg-tp4-x2 vs agg-tp2-x4 → tp2-x4 wins

2 replicas × TP=4 fails both gates (p50 6,755 / p90 10,593). Root cause: 2 replicas → ~65 concurrent/replica vs ~32 for the 4-replica layout → deeper prefill queue → higher TTFT/E2E. NVSwitch TP4 all-reduce lifts TPOT (74.5 vs 55.0). More replicas beats more TP for this prefill-dominated, high-concurrency workload. TP4 NCCL initialized cleanly on B200 NVSwitch (no Blackwell-PCIe issue).

Leg 4 — TP1 prefix-cache probe → hit rate STILL 0 key science

The most actionable finding. Prefix-cache hit rate is 0 at TP1 too, not just TP>1. One TP1 replica served 1,805,903 prefix queries against the byte-identical ~3,050-token shared header: 
vllm:prefix_cache_queries_total{engine="0"}  1,805,903
vllm:prefix_cache_hits_total{engine="0"}     0.0
So the 0% is NOT the upstream #26201 "TP>1 untested" caveat — automatic prefix caching is non-functional for Nemotron-3-Super (hybrid Mamba-2) on vLLM 0.18.1 at ANY TP. --enable-prefix-caching --mamba-cache-mode all are accepted and enable_prefix_caching=True appears in the engine config, but the Mamba-2 'all'-mode path never registers a hit. The ~3,050-token shared header is re-prefilled every request; SLO still passes on raw B200 prefill throughput + KV headroom. Re-validate on a newer vLLM with mature Mamba-2 PC.

TP1 was a science probe, not a serving candidate. It was run to prove the 0% hit rate is architecture-wide (not a TP>1 artifact) — not to evaluate it as a layout. It fails SLO by ~2× even at conc=64 (half the 130 target): E2E p50 10,559 / p90 16,940, 50,606 tok/s (~¼ the winner's node aggregate), 0 errors, 116× KV headroom unused. The bottleneck is single-GPU prefill compute, not the (non-functional, near-zero-overhead) prefix cache. TP1 failing is not evidence against B200 — it confirms the node must be packed with 4 replicas to be used properly.

Leg 5 — disaggregation → DEFERRED

4p4d / 2p6d KV-transfer disagg not run — the session was consumed by four cold-start cycles (~4–6 min each on Recreate). Given the prefill-dominated shape and that aggregated tp2-x4 already passes with headroom, disagg is low-priority. Defer to a future session if sub-4s p50 is required.

Speculative decode → CLOSED (not deployable on this stack)

Both paths blocked by the Mamba-2 backend on vLLM 0.18.1 / TP2:
  • Native MTP — crashes in MTP draft forward (size of tensor a (2) must match b (3)); pods exit 137 in a restart loop.
  • n-gram / prompt-lookup — crashes in CUDA-graph capture (mamba_attn.py:498, tensor 2 vs 6); the Mamba-2 backend assumes a fixed single-token decode shape.
The --enforce-eager workaround was rejected as unrealistic for a benchmark of record. Parked on product grounds: workload is throughput-bound at 130 concurrent (where spec-decode loses), and ITL (~17–55 ms/token) is already below human perception. Re-test only on a vLLM build that fixes Mamba-2 graph-capture + spec-decode. Note: spec-decode WORKS on g7e/SGLang (accept 0.81) with --speculative-moe-runner-backend triton — the gap is engine + draft-MoE-backend, not B200 hardware.

Recommendation to customer

  1. Deploy FP8 agg-tp2-x4, mnbt=16384, TRITON_ATTN — the validated winner: p50 4,685 / p90 8,147 at 130 concurrent, ~$0.040/1M total tokens on spot, 0 errors. ~1.5× headroom to the conc-200 SLO ceiling; comfortably covers the 25-RPS peak.
  2. Optionally adopt FlashInfer attention for ~10% latency/cost improvement — after a coherence smoke confirms the uncalibrated-fp8-scale path produces no quality regression on real Fin prompts.
  3. Do not use BF16 (fails p90), TP4×2 (fails SLO), spec-decode (blocked on 0.18.1), or TP1 (single-GPU throughput too low).
  4. Prefix caching is currently unavailable for this model — budget for full re-prefill of the shared header, or upgrade vLLM and re-validate Mamba-2 PC before relying on it.
  5. Re-test on a newer vLLM once one lands working Mamba-2 prefix caching AND Mamba-2 graph-capture + spec-decode — both could meaningfully lower TTFT / cost.
