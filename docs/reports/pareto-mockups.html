Pareto chart mockups — pick a direction

5 takes on the same data (256 records · 4 models · B200/B300). Each emphasises a different question. Tell me which one(s) to commit to.

1Per-config concurrency curves — pick a workload, read your SLO

For one workload, each line is one engine/config; each marker is one concurrency level (c=1 → c=512). Reads as: "given my use case + my latency SLO + my throughput floor, which engine/config sweep stays inside the green box?" The line tells you what concurrency to deploy at.
$/M output tok = (gpus × $/gpu-hr × 1e6) / (tok/s × 3600). Default $3.31/gpu-hr ≈ B300 spot (8 GPUs × $3.31 = $26.50/hr). Use $7.38 for B200 on-demand.
Why pickDirectly answers the deploy question: "what config + what concurrency hits my SLOs?" Each line is one operational choice — pick a curve, deploy that config at the c-level that lands in the green box.
What you loseLots of lines on a busy workload (Kimi has ~17 SGLang variants on concurrency-sweep). Either filter by model or color-by-model with one trace per (model, tag).

2Workload-faceted small multiples

3 panels side-by-side: chat-style, prefix-heavy, long-context. The leader changes per workload (Qwen owns chat, DeepSeek owns long-context). Forces you to pick the workload that matches your use case before drawing conclusions.
Why pickMost honest about the workload-dependence of the answer. Shows that "best model" isn't a global property. Parks misleading totals.
What you loseThree small charts are harder to read than one big chart. Some workloads have 3 models; others only 1 (visual asymmetry).
