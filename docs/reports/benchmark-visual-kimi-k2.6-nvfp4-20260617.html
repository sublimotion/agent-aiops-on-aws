TL;DR

Goal: characterize Kimi-K2.6-NVFP4 on one 8-GPU Blackwell node against the customer's workload (31K context, 1,024-token output, 74% prefix cache) and size a fleet for 32,500 tok/s aggregate.

  • Config: SGLang, TP4+DP2 (two 4-GPU replicas) is the best single-node layout — +19-25% over TP8 at every concurrency, lower latency. Decode-tier tricks (fp8-KV, EAGLE3, MoE-tile, MNBT) were all null/negative; wide-EP is blocked upstream; single-node disaggregation regressed 68%.
  • Hardware: B300 beats B200 by +36-43% throughput and up to −49% p50 latency — because the B200 result was limited by KV-cache capacity, not bandwidth, and B300's larger HBM relieves it.
  • Fleet sizing: measured TTFT shows a node holds ~c512 users at the 16k peak context within the 15s SLO (p99 7.9s) — so the TTFT SLO does NOT bind; aggregate throughput is the constraint → ~8 (B300) / ~11 (B200) nodes for the 32,500 tok/s peak. Autoscale to keep each node ≤~c512 (16k) / ≤~c256 (31k).
  • Cost verdict: not yet decidable — see the blocked-cost note below.

Cost / go-no-go verdict: BLOCKED (need 3 inputs)

Self-host output-only $/Mtok looks favorable at spot, but the customer's $0.338/Mtok target is a blended price dominated by input tokens (~31:1 input:output). Output-only vs blended is not a fair comparison, so we are not declaring a go/no-go.

To decide, we need: (a) customer's upstream input $/Mtok, (b) confirmed input:output ratio, (c) our measured input/prefill throughput.

1b · TTFT vs the 15s SLO (B300 TP4+DP2) — the real scale-out trigger

The customer's primary SLO is TTFT p95 < 15s (their observed avg 3.3s, p95 5.8-15s). TTFT is prefill-bound, so it depends on context length — measured here at both ends of their diurnal swing: 16k (peak-traffic hours) and 31k (quiet hours). measured (cold prompts = conservative upper bound; real 74%-cached TTFT is lower)

Flat line = 15s SLO ceiling. Lower curve = 16k context (peak hours): p99 3.9-7.9s through c512, breaches at c768 (19.7s) → ceiling ~c512-600. Upper curve = 31k context (quiet hours): fine to c256 (7.7s), breaches at c512 (19.4s) → ceiling ~c256-400 (31k c768/c1024 clipped to 25k axis; both ≫15s). Both ceilings pressure-tested to breach. Per-request decode at c1 = 166 tok/s; the TTFT (prefill) SLO binds well before the decode-rate SLO.

Scale-out trigger: TTFT-bound at ~c512 (16k peak) / ~c256 (31k quiet) per node

The operational trigger is concurrent-users-per-node gated by TTFT: a B300 node holds ~c512 users at the 16k peak-traffic context (p99 7.9s, comfortably under 15s) and ~c256 at 31k. Past those, TTFT breaches with no throughput gain (16k c768 agg 14,816 ≈ c512's 14,616 but p99 doubles to 19.7s; c1536 agg actually drops to 10,945). So provision/autoscale to keep each node ≤~c512 (16k) / ≤~c256 (31k) — never chase aggregate past the knee.

Correction (owned): an earlier version claimed "scale every ~50 users / ~25-30 nodes" — that was built on end-to-end latency mislabeled as TTFT and is withdrawn. Real measured TTFT puts per-node capacity ~10× higher. Fleet for 1,500 peak users: at the 16k peak context (~c512/node) ≈ 3-4 nodes for SLO, but aggregate-throughput still needs ~8 (B300) / ~11 (B200) — so throughput, not TTFT, is the binding constraint at 16k; size to ~8-11. (At 31k the TTFT ceiling ~c256 would need ~6 nodes — still under the throughput floor.) Gaps: TPOT/ITL not captured; TTFT on B300 only, cold prompts (real cached TTFT lower).

5 · Bottom line

  • [measured] WINNER config — TP4+DP2 (not TP8): +19-25% over TP8 at every concurrency, better latency. Peak ~3,190 tok/s on B200, ~4,490 on B300. The session-1 "~2,500 ceiling" was a TP8 artifact — parallelism layout, then hardware, were the real levers — not any decode trick.
  • [measured] 74% prefix cache reproduced both engines; workload ~26% prefill-bound; all decode-tier levers (fp8-KV, EAGLE3, MoE-tile, MNBT) null/negative on both TP8 and TP4+DP2.
  • [measured] EP/wide-EP blocked upstream (#24502); single-node 4P/4D disagg −68% (loses prefix cache + GPU starvation) — disagg is multi-node-only.
  • [measured] B300 > B200: +36-43% throughput, up to −49% p50 latency — B200's peak was partly KV-capacity-throttled, not purely BW-bound; B300's 5.6× KV pool fixes it. The SLO lever for the customer's p95 TTFT ceiling.
  • [measured] TTFT SLO does not bind; throughput does. Node holds ~c512 users at 16k peak context within the 15s TTFT SLO (p99 7.9s; breaches at c768). So sizing is set by aggregate throughput → ~8 (B300) / ~11 (B200) nodes for 32,500 tok/s. Autoscale each node to ≤~c512 (16k) / ≤~c256 (31k). (Earlier "~25-30 nodes / scale every 50 users" was from E2E-mislabeled-as-TTFT — withdrawn.)
  • [blocked] Blended cost verdict pending customer input price + token mix. Output-only is competitive at spot.
  • Open: vLLM not tuning-swept; HiCache untested; engine-winner reversal vs prior B300 unexplained.
  • Meta-lesson: the +25% win came from a carryover lesson (TP4+DP2, kimi-spec L20) the session-1 spec omitted — the fix was systematic lever coverage, not a new trick.
