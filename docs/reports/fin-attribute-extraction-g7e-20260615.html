Fin Attribute Extraction — Qwen3.6-35B-A3B: g7e vs H200 vs B200

Prefill-dominated structured extraction (ISL ~1.6K / OSL ~22) · tight 1s/2s E2E SLO @ 70 RPS peak · g7e (RTX PRO 6000 sm_120) · H200 (p5en sm_90) · B200 (p6 sm_100) · vLLM 0.22.1 FP8 · 2026-06-15→16
HEADLINE

Serve this as independent FP8 TP1 replicas behind a router — not TP2, not disaggregated. The model (3B-active MoE, ~32 GB FP8) fits one GPU with ~113× headroom, so TP-splitting buys nothing, and the ~22-token output leaves no decode phase to disaggregate. For the 70 RPS peak: ~4 H200 or ~4 B200 GPUs, or ~6 g7e GPUs at mnbt=8192 (size mnbt ≥ ISL; do not chunk below it). The key mechanism finding across three GPUs: the launch-bound wall that caps g7e at ~12 RPS/GPU is engine-specific, not hardware-fundamental — H200 (~20) and B200 (~22) both lift it ~2×, purely because vLLM's full CUDA-graph capture works on sm_90/sm_100 but crashes on g7e's sm_120, flipping the box from launch-bound to compute-bound. Per unit of SLO-safe capacity all three FP8 configs sit in a tight ~$0.096–0.116 band (H200 cheapest), so the choice is constraints not cost: g7e.48xl lowest absolute spend for ≤96 RPS, H200 best $/capacity + density, B200 max headroom. Per-request latency (~180–200 ms unloaded) is excellent on all three; the levers are mnbt sizing (+~20%) and graph capture, not kernel tuning (a measured no-op) or TP.

At the saturation knee SM is only ~43% and HBM bandwidth is idle (~0%) — neither compute- nor bandwidth-bound. The model is 35B-total / 3B-active MoE with 256 tiny experts (moe_intermediate_size=512) and a hybrid Gated-DeltaNet linear-attention path. Decode fires many small expert + scan kernels, so the SMs fill with kernel-launch and scheduling work, not dense math. The tell: TPOT climbs to 123–168 ms loaded for a 3B-active model — anomalously high unless the bottleneck is launch overhead. Same signature as Nemotron-3-Super and the bottleneck-migration thesis. Note this launch wall turned out to be engine-specific (CUDA-graph capture), not hardware-fundamental — B200 lifts it ~2×; see the B200 section. (This g7e DCGM is launch-bound at ~43% SM; the same workload on B200 with working graph capture runs SM ~99% — compute-bound.)

H200 is the cheapest per unit of SLO-safe capacity ($0.096) — it gets ~B200 throughput at a lower spot price (~10% under B200, ~17% under g7e per sustained-RPS). All three FP8 configs land within a tight ~$0.096–0.116 band, so capacity-per-dollar is roughly a wash and the choice is about constraints, not cost:
  • Cheapest whole-node for ≤96 RPS → g7e.48xlarge ($11.17/hr), lowest absolute spend and sufficient (96 RPS headroom).
  • Best $/capacity + density (4 GPUs/node) → H200 p5en if its spot price holds; ~B200 throughput, cheaper.
  • Max headroom on one node → B200 (~176 RPS/node, slight throughput edge).
Caveat: p5en spot is volatile ($13–16/hr seen); at the high end H200's edge over B200 narrows. p5e (non-EN, ~$10.64) would be cheaper still — networking is unused here (TP1, no collective).

Use 8×TP1, not TP2 — the model fits one GPU with ~113× headroom

FP8 is ~32 GB and fits a single B200 (183 GB) or g7e GPU (96 GB) with enormous headroom. So TP2 would split a model that doesn't need splitting, paying an all-reduce collective every layer for zero capacity benefit. Run independent TP1 replicas (8 per B200 node ≈ 176 RPS; 8 per g7e.48xl ≈ 96 RPS) behind a router. The fin-rag caveat that sank B200-TP1 there — a lone Blackwell couldn't pace decode for ~16 streams/replica — does not apply: this workload's output is ~22 tokens, so there's almost no decode to pace, and prefill parallelizes perfectly across replicas. 8×TP1 beats 4×TP2 here by ~2×/GPU. (Use independent replicas, not vLLM data-parallel — FP8 DP is broken on 0.22.1, see gotchas.)

The spec's decision gate — "start on g7e, escalate to B200 only if the SLO breaks before 70 RPS" — resolves: g7e is viable at 48xl (8×TP1 FP8 @ mnbt=8192 ≈ 96 RPS) and is the cheaper whole-node choice for the 70 RPS target; B200 is the denser option if peak grows.

Why NOT prefill/decode disaggregation — this is the textbook non-disagg case

Disaggregation pays off only when prefill and decode have opposite rooflines that interfere, the phases want different parallelism, and load forces you multi-node. This workload fails all three gates:

Gate for disaggThis workload
Two phases to separateOutput is ~22 tokens — it's ~95% prefill. There is almost no decode phase to isolate; a dedicated decode pool would sit idle.FAILS
Different parallelism (the only thing one engine can't fake)Model fits one GPU at TP1; prefill and decode both run fine there. No EP, no heterogeneity.FAILS
Forced multi-node70 RPS = ~4 B200 GPUs = half a node. Never crosses a node boundary.FAILS
The B200 result makes the disagg case weaker, not stronger. The instinct "it's compute-bound prefill now, so split prefill off" inverts what disagg does — disagg relocates prefill across pools, it doesn't add prefill throughput, and at the knee the single aggregated engine already runs SM ~99% (compute-bound, no idle resource to reclaim). The thing that was wrong (launch overhead) was fixed by a software lever (CUDA-graph capture), not by architectural separation. Adding a KV/state-transfer tax and a second pool would buy zero extra capacity here. Right scaling lever: replica count. This would only flip to a disagg case if ISL exploded (100K+ context forcing cross-node prefill) — here ISL is ~2,500. (If a future version sent images, the vision encoder is a third compute phase → that's E/P/D-disaggregation territory, not the text-only case measured here.)

Two software levers tested: mnbt helps ~20%, kernel tuning is dead

The launch-bound diagnosis says hardware won't help — so the levers that could are software. We tested both the spec's Axis-B knobs on the FP8 single replica (with graph capture).

mnbt=8192 extends the SLO-safe ceiling from ~10 to ~12 RPS — a ~20% per-replica capacity gain from one flag. Monotonic: bigger is better. Mechanism: the ISL is ~2,500, so any mnbt below it (2048, 4096) forces prefill chunking → extra scheduler iterations → more kernel launches, which is exactly the scarce resource on a launch-bound box. mnbt ≥ ISL runs each prefill in one step. (The spec hypothesized sweeping mnbt down to pack short-output requests — for this prefill-heavy shape the direction is reversed; size it up. Same lesson as Nemotron-3-Super.)

⛔ MoE tile tuning — a measured no-op, even though the tuner is live here

On g7e/sm_120 the FP8 MoE path is Triton (logged Using TRITON Fp8 MoE backend) and vLLM warned Using default MoE config — sub-optimal for shape E=256,N=512,fp8_w8a8. We generated the missing tile config with the ray-free tuner (batches 8–32, pruned to the launch-bound small-M regime), mounted it, and confirmed it loaded (Using configuration from /tuned/E=256,N=512,…json — warning gone).

No improvement (slightly worse, within run variance). This differs from Nemotron-3-Super in a telling way: there, tuning was inert because the kernel was FlashInfer and never read the Triton JSON. Here the kernel IS Triton and DID load the tuned config — yet still no gain. So the launch-bound knee is not in the MoE GEMM tile selection; it's the number of kernel launches and scheduling across the 256-expert + Gated-DeltaNet path. Tile tuning optimizes each GEMM's throughput; it cannot reduce dispatch count. Conclusion: don't tune MoE tiles for this model. (We initially inferred from this that a bigger GPU also wouldn't help per-replica — the B200 run below disproves that: the launch wall was graph-capture-specific, not hardware-fundamental.)

The launch wall is a software story, not a silicon tier — H200 ≈ B200 ≈ 2× g7e

Why the datacenter parts win — measured across three GPUs:
  • FP8 MoE backend = TRITON on all three (fp8.py:405). The MoE kernel path is identical — so it is not the differentiator. (Refutes the guess that Blackwell picks FlashInfer TRTLLM for this model.)
  • Full CUDA-graph capture: SUCCEEDS on H200 (sm_90) and B200 (sm_100), CRASHES on g7e (sm_120). Both datacenter parts logged Capturing CUDA graphs (decode, FULL): 100%; g7e crashed full-decode capture (1 != ISL shape assert) and effectively ran without it. This is the difference — full decode-graph capture collapses the many small per-step kernel launches into one replay, removing exactly the overhead that capped g7e. The ~2× gap tracks the vLLM version's sm-specific graph support, not raw FLOPs or bandwidth.
Bottleneck class flips: g7e at saturation was SM ~43% / HBM ~0% (launch-bound). Both datacenter parts are compute-bound at their knee: B200 SM ~99% / HBM ~31% / 786 W; H200 SM ~100% / HBM ~47% / ~688 W (H200's higher HBM engagement tracks its lower bandwidth, 4.8 vs 8 TB/s — but still compute-bound, not bandwidth-bound). The launch wall is gone; the box runs until genuinely compute-limited. Unloaded latency is identical across all three (~90–98 ms TTFT) — the win is purely the throughput ceiling.

Capacity implication: at ~20–22 RPS/replica, H200 and B200 each need ~4 replicas (half a node) for the 70 RPS peak vs ~6 g7e GPUs. Caveats: (1) vLLM 0.22.1 has a CUTLASS-DSL compile crash on both H200 and B200 in the vision-encoder path — must serve text-only with --limit-mm-per-prompt '{"image":0,"video":0}'; (2) g7e's full-graph crash may be fixable on a newer vLLM, which would lift its ceiling toward the others — so this gap is a software-maturity gap, not a pure silicon gap. Cost: H200 is actually the cheapest per unit of SLO-safe capacity — see the Capacity & cost table above.

FP8 vs BF16 — here the precision win is ~2× (and it matters)

Measured on g7e (bf16 was not run on B200). Unlike Nemotron-3-Super (where FP8 bought only ~1.25–1.4× throughput because that workload was also launch-bound at a different knee), on this model FP8 roughly doubles the SLO-safe per-replica rate (~10 vs ~5–6 RPS) and lifts saturation (~14 vs ~11 req/s). The binding constraint is the admission ceiling, and FP8's lighter per-token kernels push it up. FP8 also halves VRAM (32 vs 65 GiB) — both fit one 96 GB g7e GPU at TP1, so neither needs a collective. Recommendation: FP8.

Stage 0 — all gates passed

  • Thinking disable WORKS (the headline risk): chat_template_kwargs={"enable_thinking": False} → output negative, 2 tokens, zero <think>. With thinking on: 64 tokens of deliberation that would blow the 1s SLO. A regression that re-enables it is the single biggest deployment risk.
  • Arch registers as qwen3_5_moe (same family as Qwen3.5) — vLLM 0.22.1 loads it on sm_120 cleanly; hybrid Gated-DeltaNet (3 of 4 layers) + full-attention MoE, 256 experts, 40 layers, ~72 GB bf16 / 32 GB FP8.
  • FP8 MoE TP-divisibility: 512 / TP % 128 == 0 → TP1/2/4 OK, TP8 forbidden (moot at 2 GPU).

Engineering gotchas (g7e / vLLM 0.22.1 / qwen3_5_moe)

  • max_num_seqs default 1024 > Mamba cache blocks (754) → CUDA-graph capture refuses to start. Fix: --max-num-seqs 256.
  • FP8 + --data-parallel-size 2 is BROKEN on 0.22.1 for this hybrid GDN MoE: AssertionError: 1 != <ISL> in the all-reduce / sequence-parallel path → EngineCore dies on first real request. bf16 DP=2 worked. Workaround: independent single-GPU replicas (no DP coordinator). Consistent with the known 0.22-avoid flag.
  • First-batch JIT is brutal: fused_moe_kernel, _causal_conv1d_fwd_kernel and the GDN kernels JIT-compile on first unseen shape → 32 s cold TTFT, then 93 ms warm. Always warm up before measuring; a cold server looks wedged.
  • g7e needs --network host (no CNI on bare metal); runtime is nerdctl; start containerd first.
  • No official FP8 — used vLLM online --quantization fp8 (per-tensor dynamic). Quality vs a real extraction corpus is unverified (spec Stage 0 community-quant selection deferred).

Datacenter GPU (B200 & H200) / EKS additions:

  • vLLM 0.22.1 CUTLASS-DSL ICE on both B200 (sm_100) and H200 (sm_90) in the vision-encoder path (vit_flash_attn_wrapper → cute.compile → 🧊 ICE 🧊), fires during dummy-run profiling right after weight load. This model is multimodal; serve text-only with --limit-mm-per-prompt '{"image":0,"video":0}' to skip ViT profiling. g7e dodged it via a different ViT attention path.
  • GPU spot nodegroups on this cluster launch WITHOUT the node security group (only the cluster SG) → all pod networking (cross-node, FSx, in-cluster DNS) silently broken. Hit on both the B200 and H200 nodegroups — root cause of a long failure cascade the first time. Fix: attach the node SG (qwen3-next-bench-eks-cluster-node-*) to the instance's primary ENI.
  • Node needs the nvidia.com/gpu.present=true label or the device plugin won't schedule (0 GPUs allocatable) — bake it into the nodegroup's --labels (the H200 nodegroup did, so it attached automatically; the ad-hoc B200 node needed a manual label). Nodes have no internet egress + FSx-Lustre CSI mount fails (NID parse error) — stage weights to FSx from a CPU node, then fetch to the GPU node over the pod network (pure-Python, no apt/egress).
Method. Three platforms, identical FP8/TP1/mnbt=8192 config. g7e.12xlarge in Tokyo (us-west-2 24xl was capacity-blocked even on restart), vLLM 0.22.1, Qwen/Qwen3.6-35B-A3B bf16 + online FP8. p6-b200.48xlarge and p5en.48xlarge (H200) spot, 1 GPU each, via the qwen3-next-bench EKS cluster (us-east-2). Workload fin-attribute-extraction.yaml (random 2500-in/22-out, QPS sweep). Latency via vllm bench serve streaming percentiles; bottleneck class via in-pod nvidia-smi dmon (continuous; DCGM-exporter PROF point-samples missed the bursty peaks). All curves are single TP1 replica; per-node figures are ×8 (independent replicas, no collective — not measured concurrently, so real per-node may dip slightly from host CPU/NIC contention). Costs are us-east-2 spot, 2026-06-16 (p5en spot is volatile). All instances stopped / nodegroups deleted and held ODCRs cancelled at end of run.
