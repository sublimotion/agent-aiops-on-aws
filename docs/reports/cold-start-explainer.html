Cold Start, Explained

A tutorial on GPU LLM serving latency · 2026-06-01

1 · The Problem

What is "cold start," and why does it take 16 minutes for a 700 GB model?

Open a chat with a hosted LLM and the first token comes back in milliseconds. That is because the model is already loaded onto a GPU somewhere, with kernels compiled, caches warm, and weights pinned in HBM (the GPU's on-package high-bandwidth memory). The path from your keystroke to the first token is short.

Now imagine that GPU pool just scaled up because traffic rose, or a spot instance got reclaimed and a fresh node has to take over. The new node is bare metal: empty disk, no container, no Python interpreter, no weights. Before it can serve a single token, it has to walk through a chain of seven distinct stages — each one bottlenecked by a different physical resource (network, disk, PCIe bus, GPU silicon).

On real measurements from this lab, a brand-new B200 node loading GLM-5 on SGLang takes ~15 minutes to first token; the same model on vLLM takes ~16 minutes. A cold pull of the much larger Kimi K2.6 (585 GB) from S3 onto a fresh B300 took 46 minutes end-to-end. Even a tiny 1.7B-parameter Qwen3 model — small enough to fit in your laptop's RAM — needs ~100 seconds to first token on a B300.

The promise of this page: by the end, you will be able to look at any one of those numbers, decompose it into its seven underlying stages, and tell me which optimization lever attacks which stage and why.

2 · The Anatomy

The seven stages of a cold start

Every cold start, on every framework, decomposes into the same canonical pipeline. The wall-clock budget shifts between stages depending on model size and hardware, but the order and the mechanisms are universal. Here is what actually happens, byte-for-byte, between "kubectl apply" and "first token."

Where the seconds go (logarithmic, 1 s — 50 min)

Four real measurements from the lab. Each color is a stage. Notice how the dominant stage shifts with model size and cache state.

image pull S3/init container start weight load JIT compile CUDA graph capture first token
1

Node provisioning

Typical: 30 s — 5 min · bottleneck: cloud control plane, capacity

EKS asks EC2 for a new instance. EC2 finds a host with free GPUs in the right AZ, boots an AMI (Amazon Machine Image), runs cloud-init, joins the Kubernetes cluster, and reports Ready. None of this involves your model.

Like ordering a brand-new laptop and waiting for it to arrive at your door — the box is empty, you have not even installed anything yet.

Key insight: capacity blocks (rare hardware like B300) can take 10+ minutes to free up, because terminating instances actually have to release the slot. A "warm node pool" pre-provisions hot spares so you skip this stage entirely on autoscale.
2

Image pull

Typical: 60 s — 5 min · bottleneck: container registry bandwidth

Kubelet asks containerd to pull the serving image (vLLM, SGLang, Dynamo). For vLLM the upstream image is ~33 GB compressed: CUDA toolkit, PyTorch wheels, NCCL, Triton, flashinfer kernels, every dependency. The image arrives in layers from ECR or Docker Hub.

Like downloading the OS plus all your apps before you can boot. The 33 GB is the operating environment for your model — not the model itself.

Key insight: only 17.2% of those bytes are actually read on import. The other 83% is dead weight from CUDA samples, dev tools, alternate kernel libraries you don't use. This is the gap "lazy pull" techniques exploit.
3

Container start

Typical: 5 s — 30 s · bottleneck: filesystem overlay, init scripts

containerd unpacks layers, sets up the overlay filesystem, mounts volumes, runs init containers (which often sync model weights from S3 here), then starts the main process. Python interpreter cold-starts, vLLM imports, GPU drivers initialize.

Like the seconds between double-clicking an app icon and seeing its window appear — the OS is wiring everything up.

Key insight: if your init container is doing aws s3 sync for a 700 GB model, this stage absorbs 30+ minutes. Pulling weights here is a common antipattern; weights belong on a persistent volume or DaemonSet-managed local cache.
4

Model weight load

Typical: 30 s — 30 min · bottleneck: storage bandwidth and PCIe

vLLM reads the safetensors files from disk, deserializes each tensor, allocates HBM, and copies bytes across the PCIe bus into GPU memory. For an 8-way tensor-parallel deployment, every rank does a coordinated load of its shard.

Imagine handing 700 GB of data through a doorway one box at a time. PCIe Gen5 x16 tops out around 60 GB/s per GPU; you can't go faster than the doorway is wide.

Key insight: on local NVMe with prefetch on, page cache fills in 8.66 seconds for 585 GB. But the loader still takes 245 s after that — most of the time is per-tensor Python overhead and cudaMemcpy serialization, not raw bandwidth.
5

JIT compile and warmup

Typical: 30 s — 15 min · bottleneck: PyTorch compiler, DeepGEMM JIT

JIT stands for "just-in-time" — the compiler takes the abstract Python model definition and produces optimized GPU kernels for the exact hardware it is running on. torch.compile traces the forward pass, Dynamo lowers it, Inductor emits Triton kernels. DeepGEMM compiles fused matmul kernels per shape. flashinfer compiles attention sampling kernels on first invocation.

Like compiling a program for THIS specific GPU's silicon — same source code, different binary on B200 vs H200 vs L4. The compiler is not cheap; for big MoE models it can run for 9 minutes.

Key insight: compile output is deterministic for a given (model, vLLM version, TP, hardware, config) tuple. If you save the artifact and restore it on the next node, you skip the compile entirely. That is what an "AOT" (ahead-of-time) compile cache does.
6

CUDA graph capture

Typical: 10 s — 3 min · bottleneck: GPU launch overhead, batch-shape coverage

A CUDA graph is a recorded sequence of GPU kernel launches that can be replayed in one step, eliminating CPU-side launch overhead. vLLM captures one graph per batch size it expects to see. The default config captures 51 sizes (1, 2, 4, …, 512), each requiring a real forward pass to record.

Like rehearsing every choreography you might perform, before the show starts. More batch sizes = more rehearsal time.

Key insight: CUDA graphs are not persistent — they live in the running process and have to be re-captured every cold start. Trimming to ~10 production batch sizes (instead of 51) reclaims 60-80% of this stage with a single CLI flag.
7

First token

Typical: 1 s — 5 s · bottleneck: nothing, the model is now warm

The first real request arrives, runs the prefill phase, samples a token, returns it. The system is now in steady state — every subsequent request reuses compiled kernels, captured graphs, and KV cache pools.

The doors finally open and the show begins. Everything before this was setup.

Key insight: from the user's perspective only this number matters. Everything else is invisible operational overhead. Cold-start optimization is the discipline of pushing stages 1–6 closer to zero.
3 · Why It Matters

Three production scenarios where cold-start cost becomes a real bill

A 16-minute cold start sounds tolerable if it happens once at deploy time. The trouble is that in real production it does not happen once — it happens every autoscale event, every spot reclaim, every replica rotation. Three concrete scenarios illustrate the cost.

Autoscale during a traffic spike

replica-N goes from 1 → 4
  • HPA observes p99 latency rising, asks for 3 more replicas
  • Each new pod walks through stages 1–7 from scratch
  • For Kimi K2.6 cold path, that is 46 minutes per replica
  • Existing replica gets crushed under spike traffic the entire time
  • By the time replicas are ready, the spike is over

Spot reclaim recovery

8-GPU node dies mid-shift
  • Spot price spikes; AWS reclaims the B200 instance with 2-min warning
  • Replacement node provisions, pulls image, loads 700 GB of weights
  • Total recovery: ~16 minutes on the warm-cache path
  • If weights weren't cached on the new node: ~46 minutes (full S3 sync)
  • If you were running 1 replica, you served zero requests for that window

Multi-tenant model fleet

10 models × 3 vLLM versions × 2 hardware tiers
  • Tenant A's model is cold; first request triggers a cold start
  • If you're running model-per-tenant, every tenant pays this on first hit
  • 60 distinct (model, version, hw) combinations across the fleet
  • Without optimization: 60 × 16-min cold starts = 16 hours of cumulative warmup per redeploy
  • This is why caching strategy matters more as the fleet grows
The economic argument

A B300 instance costs ~$140/hour on spot. 16 minutes of cold start × 4 replicas = ~$150 of GPU-time spent on warmup per autoscale event. If autoscale fires twice an hour during peak traffic, the daily bill from cold-start overhead alone runs into the thousands. Cutting cold start from 16 min to 40 s does not just help latency — it directly recovers compute the user already paid for.

4 · The Levers

Four techniques, four different stages

Each of the lab's specifications attacks a specific stage of the pipeline. The point is not that one is "best" — they compose. Understanding which stage each one targets is how you reason about whether to adopt it for your own deployment.

Spec A measured attacks: stage 2 (image pull)

Make the OS download smaller

The default vLLM image is 33 GB. The slim variant produced by this lab strips out CUDA samples, alternate kernel libraries, dev toolchains, and unused PyTorch backends — leaving 15.3 GB of bytes that are actually needed at import time. A second technique, EBS prebake, ships the image already unpacked onto a snapshot volume, so the new node mounts it instead of pulling from a registry.

Imagine shipping someone a stripped-down toolbox containing only the tools they will use, instead of a full workshop. The pull stage is bandwidth-bound, so smaller bytes = proportionally less time.

Image pull (#2)
Measured win
144 s → 77 s (1.87×)
Trade-off
CI complexity to maintain a slim build
Spec B conditional attacks: stage 4 (weight load)

Stream weights faster

Tools like RunAI Streamer and ModelExpress (MX) replace the default safetensors loader with a parallel reader that overlaps S3 download with GPU memory copies. RunAI uses many concurrent threads on configurable block sizes; MX adds peer-to-peer caching across replicas on the same node.

Default loader is a single thread reading file-by-file. Streamer is dozens of threads reading the same file in parallel chunks while the previous chunk's bytes are still copying to GPU. Same data, less idle bandwidth.

0 s on local NVMe; large on S3

Spec C-EBS production-ready attacks: stages 5 + 6 (compile + capture)

Save compiled kernels and restore them

vLLM produces a torch_compile_cache/ directory containing every compiled kernel artifact keyed by config hash. Bake this directory onto an EBS volume after a single warm boot, take an EBS snapshot, and mount it on every new node. Volume creation from snapshot takes ~9 s; attach takes ~10 s; the cache then HITs and the JIT stage drops from minutes to ~25 s.

Like a browser HTTP cache, but for compiled GPU kernels. The first node pays the compile cost so the next 100 nodes don't have to. The artifact is portable across same-arch GPUs; you key it by config so different deployments don't collide.

Trade-off
Cache invalidates on any config / version / hw change
Spec E single-GPU PASS / multi-GPU blocked attacks: stages 4 + 5 + 6

Take a photograph of a fully-warmed worker

Use cuda-checkpoint (an NVIDIA tool that serializes GPU device state) and CRIU (Checkpoint/Restore in Userspace, a Linux kernel feature) to capture the entire vLLM worker process — including loaded weights, compiled graphs, pinned memory, and CUDA contexts — into a single binary blob. To start a new replica, restore the blob; the process resumes as if it had never stopped.

Like a VM snapshot, but for a process tree including its GPU state. Resuming a snapshot skips not just compile but also weight load — the weights are already in HBM inside the snapshot.

Multi-GPU bare metal blocked; vLLM-only; fragile artifact
5 · Composition

What happens when you stack the levers

The levers are not alternatives — they are complements, each attacking a different stage. Watch the bar shrink as each technique stacks on top of the previous ones. This is the realistic story of how a Ministral-3B-class deployment goes from a 100–240 s baseline to a 25–40 s autoscale floor.

Stacked cold start, Ministral-3B class on EKS, replica-N≥2

Each bar is the same workload with progressively more optimizations enabled. Lower is better.

Reading the chart

Baseline (100–240 s) is the unoptimized path: pull the upstream image, load weights from S3, compile from scratch, capture every CUDA graph size.

+A only shaves about 60 s by shrinking the image. Necessary but not sufficient — the big stages (4, 5, 6) are still untouched.

+A+B adds streaming weight load. Helpful if your weights live on S3 or network storage; a no-op if they are already on local NVMe. This is why the matrix shows a conditional win.

+A+B+C-EBS is the headline production stack. Compile cache mounted from an EBS snapshot eliminates the JIT stage in ~25 s of overhead. This is the floor for any model size, any tensor-parallel degree, any engine.

+A+B+C-EBS+E additionally restores the process state (loaded weights, captured graphs) from a CRIU snapshot. Drops the floor to 25–40 s p50, but only on the narrow set of replicas where the snapshot is valid.

6 · The Architecture Question

Three-tier separation vs the fused snapshot

The hardest production decision is not which levers to use — it is how to layer their artifacts. Spec C-EBS keeps the image, the compile cache, and the weights as three separate caches. Spec E fuses all three (plus process state) into a single snapshot blob. Both work; they have very different operating cost profiles.

Three-tier (A + B + C-EBS)

Tier 1 · ~3 GB · invalidates on driver/CUDA bump
Slim image (env: CUDA, vLLM, drivers)
independent
Tier 2 · ~1–5 GB/key · invalidates on vLLM/config/hw bump
Compile cache, EBS snapshot, keyed by config hash
independent
Tier 3 · 6 GB–700 GB · invalidates on weights update
Model weights (S3 + MX/RunAI)
Property: a vLLM bump rebuilds tiers 1+2 but reuses all weights. A weights swap reuses tiers 1+2.

Fused (Spec E snapshot)

One artifact · weights + 4 GiB host state + 1 GiB×TP GPU state
Env + compile cache + weights + process state, all fused
single artifact, no internal layers
Property: ANY change — new vLLM, new weights, new driver, new config — invalidates the whole blob. Full produce path required to rebake.

The fleet arithmetic

Suppose you operate 10 distinct models, each running on 3 vLLM versions (current, previous, canary), on 2 hardware tiers (B200 and H200). That is 60 deployment combinations.

The three-tier path needs 16 artifacts total: 6 env images (one per vLLM×hw) + 10 weights stores. Compile caches are produced lazily and cached on EBS volumes shared across keys.

The fused snapshot path needs 60 snapshots — one per (model, version, hw) tuple — and a fresh produce path for any of those that go stale. The snapshot's compile-cache contribution is reproducible by C-EBS at a fraction of the bake cost; the unique value snapshot adds is the process state, not the compiled artifacts.

7 · Decision

Which path should you choose?

Walk through this tree top to bottom. The default answer is the three-tier stack; snapshot is an opt-in for the narrow case where its trade-offs make sense.

Question 1
Is your stack frozen for at least one week between version bumps? (vLLM, driver, weights, config all stable.)

No → bumps invalidate snapshots faster than you can re-bake them. Use three-tier (A+B+C-EBS). Stop here.

Question 2
Is your serving engine vLLM? (Not SGLang, not Dynamo runtime, not TGI.)

No → Dynamo Snapshot is vLLM-only in preview. SGLang fleets must use three-tier. Use three-tier (A+B+C-EBS). Stop here.

Question 3
Is autoscale latency load-bearing for your SLO? Specifically, would shaving cold start from 50–120 s to 25–40 s materially improve user experience or recovery RTO?

No → the operational cost of maintaining 60 snapshots outweighs the benefit. Three-tier is fine.

Question 4
Is your deployment single-GPU, or single-node multi-GPU running inside a container with peer GPU device nodes hidden? (Multi-node TP > 1 is currently unsupported.)

No → multi-node TP via Dynamo Snapshot is an open research area. Use three-tier.

All four Yes: adopt Spec E snapshot on top of three-tier. Snapshot's value-add is process state (CUDA graphs, pinned memory, NCCL state), not compiled kernels — C-EBS handles those at a fraction of the bake cost. The combination delivers ~25–40 s p50 on autoscale events that fire on a stable stack.
Default for everyone else: the three-tier stack — slim image (A), MX/RunAI weights (B), EBS-snapshotted compile cache (C-EBS). This is the rule encoded in .claude/steering/tech-stack.md: it's cheaper to operate, degrades gracefully under fleet churn, and works with both vLLM and SGLang.
8 · What's Next

Open frontiers

Not everything is solved. These are the directions the field is moving in — useful context whether you are choosing a stack today or watching to see what becomes practical next year.

Multi-node TP > 1 snapshot

  • Cross-node CRIU restore is unsolved — NCCL state, IB/EFA fds, peer GPU enumeration all break
  • NVIDIA's K8s snapshot-agent handles single-node only
  • Fallback today: full cold start for any TP > 1 deployment that snapshot doesn't reach

SGLang process snapshot

  • Dynamo Snapshot is structurally vLLM-only in preview
  • SGLang's hierarchical cache and DeepGEMM JIT paths are not in the snapshot's scope
  • Models like GLM-5, Kimi K2.6, Nemotron-Super are bound to three-tier until upstream lands SGLang support

GPUDirect Storage path

  • True NIC-to-HBM DMA would skip the CPU bounce buffer that bottlenecks weight load
  • Requires a CUDA driver patch + RDMA NIC (only on p5/p5e InfiniBand today)
  • EFA is kernel-bypass but still bounces through CPU; not the same primitive
Where the floor goes from here

The current measured floor on Kimi K2.6 (8×B200 TP=8) is 245 s of weight load after page cache fills. That is not bandwidth-bound — the NVMe delivers 67 GB/s. It's per-tensor Python overhead and serialized cudaMemcpy calls. The two paths below it are ModelExpress same-node P2P (replicas share weights via NVSwitch at 250 GB/s, untested) and vLLM-internal batched H2D copies with pinned memory (out of scope for this lab, requires upstream work). Either gets the floor closer to ~30 s.

9 · Reference

Glossary

Quick definitions for the acronyms used above. Skip if you already know them.

JIT
Just-In-Time compilation. The compiler runs at first invocation, producing GPU kernels tailored to the exact runtime shapes and hardware.
AOT
Ahead-Of-Time compilation. The compiler runs once, persists artifacts to disk, and subsequent runs load the prebuilt kernels instead of recompiling.
CUDA graph
A recorded sequence of GPU kernel launches that can be replayed in one CPU call, eliminating per-launch overhead. Captured at runtime, not persistent across processes.
CRIU
Checkpoint/Restore In Userspace. A Linux feature that serializes a running process tree (memory, file descriptors, threads) to disk and restores it later, possibly on a different machine.
cuda-checkpoint
NVIDIA tool that serializes GPU device state (HBM contents, CUDA contexts, streams) so CRIU can checkpoint the host-side process around it.
FSR
Fast Snapshot Restore. AWS feature that pre-warms an EBS snapshot in a target AZ so volumes created from it don't pay the lazy-load penalty on first read.
NCCL
NVIDIA Collective Communications Library. Implements all-reduce, broadcast, and other multi-GPU collectives used in tensor-parallel inference.
MTP
Multi-Token Prediction. Speculative decoding where a small drafter model predicts the next K tokens, then the main model verifies in one forward pass.
P/D disagg
Prefill/Decode disaggregation. Separates the compute-bound prefill stage (processing the prompt) from the memory-bound decode stage (generating tokens) onto different GPU pools for better utilization.
NVMe instance store
Local SSD attached directly to an EC2 instance via NVMe. Ephemeral — data is lost when the instance terminates — but delivers tens of GB/s read bandwidth.
EBS
Elastic Block Store. AWS network-attached block storage. Persists across instance termination, supports snapshots, attaches over the network at ~1 GB/s.
HBM
High-Bandwidth Memory. The on-package DRAM stacks that supply GPU compute units. B300 has 275 GB per GPU at ~8 TB/s.
PCIe
The bus connecting CPU and GPU. PCIe Gen5 x16 tops out around 60 GB/s — the doorway through which weight data travels from disk to HBM.
