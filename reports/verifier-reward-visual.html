Drop the Gate, Raise the Threshold

59 iterations discovered that v009 alone at 4/4 unanimous outperforms the v001∩v009 ensemble. On SWE-bench Verified (483 patches): precision 0.92 [0.79, 0.97], only 3 FPs. Simpler (4 calls not 5), cheaper ($0.030/patch), and more precise than the ensemble.

Context: The Fix-to-Pass Gap

The Problem

Coding agents fix bugs but don’t solve them

On SWE-bench Lite (50 real GitHub issues from Django, Flask, scikit-learn, etc.), coding agents generate patches that look correct at very high rates — but most don’t actually pass the project’s test suite.

Claude Sonnet98% produce a patch → 12% pass tests86pp gap
Claude Opus98% produce a patch → 12% pass tests86pp gap
Qwen3.5 122B86% produce a patch → 9% pass tests77pp gap
Devstral 24B96% produce a patch → 9% pass tests87pp gap

The gap is enormous across all model tiers. You get a pile of plausible-looking patches with no way to tell which ones actually work — without running the full test suite (expensive, slow, often requires complex environment setup).

The Hypothesis

A verification skill can close the gap

Instead of running tests, use a second LLM call as a judge: give it the bug report and the proposed patch, and ask whether the patch actually fixes the bug. If the verifier is precise enough, it can select the good patches from the pile.

  • Precision matters most — a false positive (shipping a broken patch) is far worse than a false negative (rejecting a good one)
  • Cost must be low — verification should cost pennies, not dollars
  • No test execution — the skill must work from the diff alone

The Verification Gap

When a coding agent generates a patch, you face an asymmetry: the agent is confident it fixed the bug, but you have no way to know without running tests. The verification gap is the space between “the agent produced something” and “the fix actually works.”

Why patches look right but aren’t

Agents are optimized to produce plausible code. They target the right file, the right function, the right bug — but introduce subtle logic errors: wrong boundary conditions, missing edge cases, incomplete fixes that address the symptom but not the root cause. These patches pass code review but fail tests.

Why test execution is expensive

Each SWE-bench issue requires cloning the repo at a specific commit, installing version-specific dependencies, and running the test suite in an isolated container. This takes 2-10 minutes and requires Docker infrastructure. For N candidates across M issues, cost scales as O(N×M).

The verification skill alternative

A $0.048 LLM call that takes 2 seconds and needs no infrastructure. If its precision is high enough, it can filter the patch pile before expensive test execution — or replace it entirely for triage. The key question: can prompt engineering alone achieve sufficient precision?

v001 gate hurts at high base rate

At 51% gold pass rate, v001 removes correct patches faster than incorrect ones. Dropping it: +0.14 precision, +2x recall, 2 fewer FPs, 1 fewer call. The confirmatory gate only helps when base rate is low (<20%).

Unanimity is the key

Requiring all 4 v009 runs to agree (4/4) catches 2 extra FPs over the 2+/4 threshold. True positives consistently get 4/4 lc. False positives occasionally get 3/4 but rarely 4/4.

3 stubborn FPs remain

django-15103 and xarray-6992 get 4/4 lc even at temp=0.7 with 6 runs. django-13590 is a new holdout FP. These require codebase-level completeness reasoning beyond diff-only rubrics.

But the model applies it equally to correct and incorrect patches — it can’t distinguish “genuinely incomplete” from “potentially incomplete.” Threshold tuning on the existing v009 rubric produces a better tradeoff than any new rubric.

Simple beats clever: same rubric, better threshold

After testing 4 new rubrics and various ensemble strategies, the best improvement came from two simple changes: drop the v001 confirmatory gate and require unanimous v009 agreement. Precision improved from 0.78 to 0.92, recall doubled, and cost dropped 37%.

Why Skills Amplify: Two Mechanisms

Mechanism 1: Patch Quality

Better models produce richer error signals

Frontier models generate patches with more distinctive error signatures. Claude’s false positives have subtle but detectable logic flaws (regex scope, missing edge cases). Qwen3.5’s false positives on small diffs (<2K chars) lack surface area for the adversarial rubric to find bugs.

Claude FPsv009 finds bugs in 100% — 0/4 lc each
Qwen3.5 FPsv009 misses bugs in 50% — flask-4992 gets 3/3 lc
Mechanism 2: Harness Surface Area

Richer diffs give the skill more to work with

OpenCode produces multi-file, multi-hunk diffs (8-12K chars) regardless of model. SERA produces surgical 2-line patches (1.5K). The adversarial rubric needs surface area to find bugs — larger diffs provide more attack vectors.

OpenCode diffsMedian 8-12K → prec 0.50-1.00
SERA diffsMedian 1.5K → prec 0.33

Both mechanisms compound: a frontier model × rich harness = maximum amplification. A weaker model × minimal harness = minimal amplification. The implication: invest in model capability AND harness tooling together.

Diff Style Determines Verifier Signal

The harness — not the model — controls the diff style. OpenCode produces large, multi-file diffs regardless of which model generates them. The verifier’s precision correlates with diff size because adversarial reasoning needs surface area to find bugs. Both Qwen3.5 FPs are on small diffs (<2K), the same size range where SERA patches live.

Autoresearch: How Autonomous Iteration Found the Skill

The verification skill was discovered through an autonomous research loop: hypothesize → run experiment → log → decide. No human rubric engineering — the agent iterated through 54 experiments, systematically testing and discarding hypotheses until it found the adversarial framing breakthrough.

The Loop

Skill Iteration Protocol

  1. Read latest sweep results and error analysis
  2. Hypothesize one specific improvement (rubric, model, threshold, ensemble)
  3. Run experiment — one variable at a time, mandatory smoke test
  4. Log result to immutable table (even failures)
  5. Decide — keep, discard, escalate, or terminate

Guardrails: circuit breakers ($5/sweep), one variable per iteration, never edit gold labels, immutable rubric versions, holdout reserved for final candidates only.

Autonomous Discovery: Adversarial Framing

The agent discovered that inverting the verification prompt from “evaluate correctness” to “find the bug” eliminates all false positives. This is a non-obvious insight — confirmatory rubrics were the standard approach across 8 prior versions.

Systematic Elimination

After the breakthrough, the agent methodically tested every remaining lever (14 rubric versions, 5 models, extended thinking, multi-turn, decomposition) to prove the recall ceiling is fundamental. A human would likely have stopped after 5-10 negative results.

Key Negative: Self-Critique Hurts

The agent tested adversarial self-critique in generation (T5). It discovered that a model can find bugs in OTHER models’ code but not its own — fix rate dropped 54%→30%. This “blind spot” finding validates external verification as the correct architecture.

The Breakthrough: Adversarial Framing

Confirmatory (v001)

“Evaluate whether this patch is correct”

Score the patch on 6 criteria: problem alignment, minimality, test safety, logic correctness, scope, completeness.

“You are a patch verification expert. Evaluate the patch on each criterion. Score each 0.0 to 1.0.”

Precision: 0.29 — Biased toward confirming patches that “look right”

Adversarial (v009)

“Assume this patch is wrong — find the bug”

3 steps: identify what the patch claims, attack the claim, judge based on whether you found a bug.

“You are a code reviewer whose job is to FIND BUGS. Assume the patch is incorrect. Only clear if you cannot find any plausible bug.”

Precision: 0.92 (4/4 unanimous, n=483) — Actively hunts for failure scenarios

The best config (T10b) uses v009 alone: 4 adversarial runs (1×t=0.0 + 3×t=0.3), requiring unanimous agreement. True positives survive all 4 attacks; false positives fail at least once. The v001 confirmatory gate was dropped — it hurts precision at high base rates.

13/91 errors (14%). Sonnet reformats entire files (66-135K chars for a 3-line fix). Even minimal oracle diffs (525 chars) get rejected — the problem is semantic, not noise.

Semantic Mismatch: The Root Cause

Verifier evaluates problem completeness. Tests check specific behaviors. A patch fixing formfield() but not deconstruct() is genuinely incomplete but passes narrow tests. Both Haiku and Sonnet independently agree.
