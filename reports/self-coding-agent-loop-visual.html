Continuous-calibration RLVR what this actually is

Once you squint, the rolling-rounds structure reveals the real design: this isn't "Phase 1 then Phase 2" — it's a single RLVR loop with a verifier that co-evolves with the policy. The two phases differ only in which labels are available, not in the underlying algorithm. The name we'd use for this in an RL textbook: continuous-calibration RLVR, or model-verifier co-training.

Policy side (the coding agent)

Each round, the policy is updated using the verifier's reward. Gen-(N+1) is produced by GRPO/STaR on Gen-N's outputs weighted by verifier scores. Standard RLVR.

The key property: the policy gets stronger each round. Its outputs shift. Things that looked "obviously broken" to Gen0 now look "subtle edge case" at Gen5.

Verifier side (the reward model)

Each round, the verifier is recalibrated using fresh gold labels from round_N's Docker eval. The verifier sees what the new-and-stronger policy actually produced, and adjusts — new feature distributions, new failure modes, new edge cases.

Without this loop, the verifier would drift: trained on Gen0 outputs but scoring Gen5 outputs. By the time Gen5 is generating patches the verifier's training set couldn't anticipate, the reward signal is noise. The co-training loop prevents that.

The actual Phase 1 → Phase 2 transition is just a reduction in gold-label density: from "every round's data is Docker-eval'd" to "periodic 100-task audits". Policy update logic is identical. Verifier recalibration logic is identical. Only the rate of fresh labels changes.

Why this framing matters

No big-bang transition

The spec originally treats Phase 2 as a new regime. With continuous calibration, it's just a parameter change. Lowers risk: we're not flipping a switch; we're slowly reducing gold-eval coverage.

Drift trajectory proves trust

If ECE stays flat across 5 policy generations under identical inputs, that's strong evidence the verifier can keep up with the agent's evolution. Stronger than any single calibration number.

Gold labels become a safety net

In Phase 2, gold eval isn't the reward — it's the drift detector. 100 tasks × every 3 iterations ≈ $10. Cheap insurance against the verifier silently going wrong.

But the verifier must be recalibratable

Loop 1's `bootstrap_new_distribution` path has to actually converge with ~200-500 fresh labels. M2 showed the Claude-trained RF flatlines OOD. Each round's 800 gold labels plus drift_audit's 300 should give ~1,100 labels to retrain on — well above the bootstrap minimum.

Rubric is still Claude-specific

RF retrains freely round-over-round, but v009 rubric doesn't. If the policy's outputs drift far enough from what v009 was tuned for, V1b_rubric fires and manual rebuild is the only path. Planned gap in the flywheel.

Formally, this is co-training

Policy and reward model co-evolving with a shared data stream. Related: AlphaGo's value net updates during self-play. Different: we anchor to external gold tests to prevent reward hacking.

Risk this framing introduces: reward hacking

Co-training policy and verifier creates a well-known failure mode: the policy learns to produce outputs that score high on the verifier without being correct. Gold labels anchor us — but only if they catch the hack. Three guardrails:

  • drift_audit_300 gold eval every round — if verifier score ↑ but gold pass rate ↓, that's literal reward hacking, full stop.
  • Phase 2 gate requires 3 consecutive rounds of stable agreement — single-round alignment could be noise; 3-round monotonic stability is much harder to hack.
  • v009 rubric is deliberately NOT retrained automatically — the RF adapts freely but the rubric stays adversarial. Hacking both simultaneously is strictly harder.

Dataset splits revised 2026-05-10 · rolling rounds

Partition by instance, into rolling rounds so we can measure verifier calibration AND drift AS the base model changes, while keeping a final stress set truly unseen all the way through. Solves two problems: (a) one static held-out set gives one post-hoc number, not a drift trajectory; (b) if we update the base model mid-experiment, we need fresh eval data each round or we're measuring memorization.

Why instance-level matters

The rolling-rounds structure

Five training rounds. Each round has its own 300-instance round-N control that the model has not been trained on at round N's start. After round N completes, that control set joins the training pool for round N+1 — it's spent its "unseen" value, so we recycle it as labeled data. A fresh 300 instances emerge from the pool as round N+1's control. Meanwhile a final stress set of 500 and a drift audit set of 300 stay untouched by training at every round.

This gives us five independent data points for every metric — model gold-pass rate, verifier ECE, verifier precision, verifier-gold agreement — across a series of increasingly-trained models. That's a trajectory, not a single number. If the verifier starts strong and drifts as the model improves, the curve shows it. The final stress set + drift audit set catch anything the rolling controls miss.

Why this gives us a drift trajectory, not a single point

Traditional eval: train once, test once, one number. We don't learn when the verifier started disagreeing with gold or whether the model is still improving. With rolling rounds, the same 300-instance drift_audit_300 set is re-evaluated under every Gen-N checkpoint. Same inputs, different models, five timepoints per metric.

What each round measures

After each round we produce a Gen-N checkpoint and run three evals. Combined across 5 rounds, we get curves for four metrics.

MetricWhat it answersDrift signal
Gen-N gold pass rate on round_N_control Is the model still improving? Plateau or regression → stop training; activate Loop 3/4
Gen-N gold pass rate on drift_audit_300 Is improvement general or specific to this round's data? Round control improves but drift audit doesn't → overfitting to each round's distribution
Verifier ECE on drift_audit_300 Is the verifier still calibrated as the model changes? ECE rising ≥0.05 round-over-round → verifier drift; trigger recalibration
Verifier-gold agreement on drift_audit_300 Do verifier pass/fail decisions still match Docker gold? Precision drops below drift-alarm (0.80) → pause, return to Loop 1

Why this structure answers the right question

Calibration across model versions

drift_audit
The same 300 instances are gold-eval'd and verifier-scored under Gen1, Gen2, Gen3, Gen4, Gen5.
Same inputs, different models → isolates verifier behavior from data drift. If Gen3's patches on these 300 score differently from Gen1's patches on the same 300, that's pure model-output drift — exactly what Phase 2 will face in the wild.

Fresh vs recycled separation

round_N_control
Round N evaluates on 300 instances Gen-N has never seen, but those 300 become training data for Gen-(N+1).
Avoids wasting data: every instance is either training or eval-then-training, never just wasted. The "never seen before this round" guarantee is per-round, not absolute.

True unseen at end

final_stress_500
500 instances written-locked through all 5 rounds and Phase 1. Read only for end-of-Phase-1 and Phase 2 evaluation.
The "would this model work on truly novel problems" number. If Gen5 beats Gen0 on round_5_control but can't beat Gen0 on final_stress, the improvement was round-data-specific and Phase 2 claims collapse.

Phase 2 entry requires drift monotonicity

all sets
New gate: verifier-gold agreement on drift_audit must stay above SFT-ready level (0.85 precision) for at least 3 consecutive rounds before Phase 2 transition.
Guards against "verifier looked good at Gen1 but was actually tracking superficial features that Gen2 broke." Monotonic 3-round stability is much stronger evidence than a single snapshot.

V1b_bootstrap

Mandatory (not conditional). Target = Qwen3.5-27B × OpenHands v0.54. 200-label lower bound, 400-500 budgeted if ECE slow to converge.

V1b_validate

Checks the recalibrated RF against the readiness-level table. Pass at V1b-unlock (≥0.70 precision) unlocks Arms C/D/E to start — lower than SFT-ready because Arm C measures empirical convergence, not deployment readiness.

V1b_rubric

Only fires if RF is well-calibrated but precision still fails — the v009 rubric itself is the bottleneck. v009 is Claude-specific (T4 showed Devstral 0.20, Nova Pro 0.14). No tested backup exists (E_constraint_agent negative).
