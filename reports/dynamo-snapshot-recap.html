Two snapshots, two different things

The cold-start lab now hosts two techniques with the word "snapshot" in their name. They attack different stages and rely on completely different primitives. Conflating them will produce incorrect steering rules.

Spec C-EBS · Compile-cache snapshot

Bake vLLM's torch_compile_cache directory onto an EBS volume, take an EBS snapshot, mount on each fresh node via the EBS CSI driver. Eliminates the JIT/compile + CUDA-graph capture stages. AOT cache HIT in ~25 s overhead. Block-storage operation, no kernel features required.

Spec E · Dynamo Snapshot (this report)

cuda-checkpoint serializes GPU device state, then CRIU dumps the full process tree (memory, fds, CUDA contexts) to disk. Restore brings back a fully warmed-up vLLM worker. Eliminates the model load + JIT + first-token warmup stages in a single step. Process-level C/R, requires kernel CAP_CHECKPOINT_RESTORE + driver 580.xx+.

When to reach for which

Spec C-EBS is production-ready today on EKS for any model size, any TP. Use it as the default. Spec E is the single-GPU replica-N≥2 fast-path: when your autoscale signal arrives and a warmed worker artifact already exists for that exact (model, engine version, driver, hardware) tuple, you skip not just compile but also weight load and first-token warmup. The two compose: a fresh node can mount the EBS compile cache and restore from a Dynamo snapshot.

Why Gate 2 is a measurement artifact, not a bug

The 4.14 GiB artifact decomposes as: 1.7 GiB EngineCore pages (1.12 GiB FP16 weights pinned + 0.6 GiB torch/CUDA driver state), 0.9 GiB across ~28 memfd-backed regions, the remainder Python interpreter and shm process state. The ~3 GiB tail is fixed-overhead — independent of model size. Verified with sleep(level=2): artifact drops to 1.51x but Gate 1 fails because wake_up reloads weights on a different CUDA context post-restore. Conclusion: sleep(level=1) is the only correctness-preserving level, and the >2x ratio on sub-3-GiB models is expected.

Spec amendment recommended

The spec's artifact ≤ 2× weights threshold is inappropriate below ~3 GiB. Replace with a size-tiered rule already drafted in Stage 0 pass criteria: weights < 3 GiB → artifact ≤ weights + 4 GiB; weights ≥ 3 GiB → artifact ≤ 2× weights. The bridging cell measurement converts the correctness-only gate failure on Qwen3-0.6B into a passing scientific data point that predicts success on every model the spec actually cares about.

Technical findings

Things you only learn by running the build

CRIU PR #3021 / #3022 conflict

There is no NVIDIA-hosted CRIU fork
  • The "AIO + parallel-memfd patches pending merge" referenced in the upstream Dynamo blog map to two upstream PRs against checkpoint-restore/criu, both authored by dfeigin-nv.
  • PR #3022 — pie: restore VMA pages with native AIO
  • PR #3021 — restore: open memfd-backed VMAs in parallel
  • Both are mergeable individually against criu-dev, but they conflict on criu/mem.c. Operators must hand-resolve to get both.
  • Decision in the bridging cell: PR #3021 only — parallel-memfd is the dominant restore-time win for memfd-backed pytorch tensors; AIO is incremental on top.

io_uring + uvloop seccomp workaround

vLLM's libuv backend trips CRIU 4.2
  • Dumping a process tree containing uvloop (vLLM transitive dep) fails: Unknown shit 600 (anon_inode:[io_uring]).
  • criu check --feature uring returns "Unknown feature uring" even with PR #3021 merged.
  • Upstream PR #1597 (GSoC io_uring C/R) has been open since 2021, not part of NVIDIA's patch set.
  • NVIDIA's snapshot-agent (Go DaemonSet, protocol/checkpoint.go:188-204) injects a localhost seccomp profile that blocks io_uring_setup/_enter/_register, forcing libuv to fall back to epoll.
  • For bare-host runs the equivalent is UV_USE_IO_URING=0 or running pure pytorch (which is what the bridging cell did).

Host-RAM constraint

cuda-checkpoint copies device state to host before CRIU dumps
  • First attempt with gpu_memory_utilization=0.85 on g6.xlarge (15 GiB RAM, 23 GiB L4) failed with Could not checkpoint: out of memory.
  • Until the GMS path lands (blocked on a CUDA driver patch), host RAM must exceed peak GPU allocation.
  • Production rule: host_RAM ≥ 1.2 × peak_GPU_alloc + 4 GiB OS.
  • For Mistral-Small-4 in 24 GiB this means choosing g6.4xlarge/g6.8xlarge over g6.xlarge purely for checkpoint headroom — not for compute.

sleep(level=1) is the only correctness-preserving level

level=2 unloads weights, breaks restore
  • vLLM sleep(level=1) released 8.85 GiB on Qwen3-0.6B (282 MiB still resident); artifact 4.14 GiB.
  • vLLM sleep(level=2) dropped artifact to 2.14 GiB (1.51x — Gate 2 PASS), but Gate 1 FAILED: wake_up after restore reloads weights from disk on a different CUDA context than the one CRIU restored. First generated token came back as 0.
  • The cuda_plugin CUDA_CHECKPOINT macro walks all CUDA-using PIDs in the tree — pre-calling cuda-checkpoint from a shell harness causes a re-lock that misses vLLM's V1 EngineCore subprocess context. Just call criu dump after sleep() and let the plugin handle device state.

cuda_plugin path resolution

Built with --prefix=/usr/local, loaded from /usr/lib/criu
  • make install-cuda_plugin places cuda_plugin.so at /usr/local/lib/criu/, but CRIU's default plugin dir is /usr/lib/criu/.
  • Without an explicit -L flag (or symlink), CRIU silently does NOT load the plugin and the dump fails on the first CUDA mapping with a misleading handle_device_vma plugin failed: No such file or directory error.
  • Diagnostic giveaway: grep cuda_plugin dump.log returning empty.
  • Fix: ln -sf /usr/local/lib/criu/cuda_plugin.so /usr/lib/criu/cuda_plugin.so.

pycriu install breaks system Python

AL2023 system Python 3.9 + pip wheel build
  • sudo make install fails at install-lib with error: invalid command 'bdist_wheel'.
  • Fixing it requires pip install wheel setuptools at root which clobbers rpm-managed packaging.
  • Skip install-lib entirely: sudo make install-criu install-cuda_plugin is sufficient. Python bindings are not required for the criu dump/restore CLI flow.
p5e anchor cell · HALT

Why bare-EC2 multi-GPU is a dead end today

The Gemma-4 anchor cell on p5e.48xlarge (8× H200 spot at $16.89/hr) was supposed to validate the Hopper-class restore against Modal's 22 s AOT-HIT floor. The cuda-checkpoint primitive itself was healthy on Hopper (driver/CUDA stack is sm-agnostic) — but CRIU dump failed at fd-level on the bare host, and the diagnosis ruled out a CRIU-only fix.

Failure signature

56312 fdinfo 9: pos: 0 flags: 100002/0x1
Error (criu/files-ext.c:98): Can't dump file 9 of that type [20666] (chr 195:255)
Error (criu/cr-dump.c:1701): Dump files (pid: 56312) failed with -1
Error (criu/cr-dump.c:2130): Dumping FAILED.

fd 9 = /dev/nvidiactl (chr 195:255). 50 more like it across /dev/nvidia0..7 and /dev/nvidia-uvm.

Root cause: NVIDIA driver behavior

  • A 5-line script — torch.cuda.init(); torch.cuda.set_device(0); torch.randn(1024, device='cuda:0') — launched with CUDA_VISIBLE_DEVICES=0 opens 51 fds across all 8 /dev/nvidiaN + /dev/nvidiactl + /dev/nvidia-uvm.
  • CUDA_VISIBLE_DEVICES gates which device cudaSetDevice can target, NOT which device files the driver opens.
  • The driver always enumerates and probes all nodes for NVLink/NVSwitch topology discovery.
  • cuda_plugin only registers HANDLE_DEVICE_VMA, CHECKPOINT/PAUSE/RESUME_DEVICES; it does NOT register HANDLE_DEVICE_FD.
  • Bare-fd opens with no associated VMA fall through to CRIU's generic dump_unsupp_fd → -ENOTSUP.

Why g6 worked but p5e doesn't

  • g6.xlarge has 1 GPU. Driver only opens /dev/nvidia0 + /dev/nvidiactl + /dev/nvidia-uvm.
  • Whatever fd configuration produced the bridging cell's clean dump was small enough that fds were either VMA-backed (handled) or simply absent.
  • On p5e, the volume of bare-fd opens to peer GPUs is what trips files-ext.c:98.
  • The --external dev[195/255]:nvidiactl escape hatch targets mountable block devices, not character-device fds — wrong primitive for this fd class.
Pivot: containerized execution

NVIDIA's K8s-native snapshot-agent sidesteps this because nvidia-container-runtime injects ONLY the requested GPU's device nodes via OCI hooks. The workload pod literally doesn't see /dev/nvidia[1-7] because they're not bind-mounted. CRIU then has nothing to dump for those non-existent fds. Three possible paths forward, in priority order:

  1. Containerized execution (nvidia-container-runtime --gpus '"device=0"') — same trick the upstream agent uses, runs on plain Docker/containerd without K8s.
  2. Upstream cuda_plugin patch adding HANDLE_DEVICE_FD — file upstream, no immediate timeline.
  3. Wait for NVIDIA to publish the missing CRIU pieces — neither dfeigin-nv/criu nor checkpoint-restore/criu has HANDLE_DEVICE_FD as of 2026-05-30.

Per the spec halt-conditions, this is documented as a multi-GPU instance issue, not a Hopper sm_90 hardware issue. Gates 1/2/3 are not measured for the p5e cell because dump failed before artifact production; the anchor TTFT comparison vs Modal is moot for this iteration.

Operational lessons

What the spot pool and ssh taught us

AMI-bake pattern

~$0.05 add cost, saves ~25 min per reclaim
  • Phase 1: on-demand g6.xlarge, ~30 min CRIU + cuda-checkpoint build.
  • Phase 2: aws ec2 create-image --no-reboot, ~5 min, AMI ami-041914c9e9b61b15e.
  • Phase 3: spot from AMI — launch in 30 s, ssh-ready in 1 min, gates run.
  • Survived two reclaims; second spot fulfilled in 30 s.
  • Tag the AMI with CRIU sha + PR refs so it can be rebuilt deterministically when criu-dev moves.

Spot reclaims, twice

g6.xlarge us-west-2b/d both reclaimed mid-cell
  • First reclaim: 85 min uptime, instance-terminated-no-capacity, lost the entire raw-spot CRIU build (no AMI yet).
  • Second reclaim: 30 min uptime mid-gate-run, with AMI in place. Recovery time 6× faster.
  • NVMe instance store does NOT persist across AMI — venv + weights re-stage every spot (~3 min for Qwen3-0.6B).
  • For larger models, push venv + weights tarball to S3 from the build phase; restore on each spot via aws s3 cp.

--tcp-established + ssh foot-gun

CRIU dump killed the active SSH session
  • First gate run exited with "Connection to <ip> closed by remote host" right after criu dump started.
  • --tcp-established froze every TCP connection in the wrapper's net namespace; the orchestrator was a child of sshd, so the dump touched a socket that propagated back.
  • The dump itself probably completed fine, but the result was unreadable.
  • Fix: nohup bash run-bridging-gates-v2.sh > /mnt/nvme/smoke/logs/orch.log 2>&1 & disown. SSH stays alive; read results from the log file after the run.

pip install on root EBS fills /tmp

vLLM 0.10.2 wheel extraction blew past free space
  • NVIDIA AMI uses ~30 GB of the 250 GB EBS root; pip install vllm==0.10.2 needs ~50 GB site-packages plus temp wheel extraction.
  • [Errno 28] No space left on device on first try.
  • Fix: TMPDIR=/mnt/nvme/pip-tmp pip install --cache-dir /mnt/nvme/pip-cache .... NVMe instance store has 233 GiB free.

Cross-family AMI is sm-agnostic

AMI baked on Ada (g6 sm_89) launched cleanly on Hopper (p5e sm_90)
  • nvidia-smi enumerated all 8× H200 (143771 MiB each); cuda-checkpoint, criu, cuda_plugin all functional.
  • No re-bootstrap needed. The userspace stack is sm-agnostic as long as the driver major (580+) covers all targets.
  • One AMI can target Ada → Hopper → Blackwell. The CRIU dump failure on p5e is mount-namespace, not stack version.
